literal, and so a future non-HTML metadata route (a sitemap) cannot detonate it.

delta 1, delta 4/SC-4a, SC-4b, SC-4h, SC-4d, delta 8, SC-4f — six of the seven from one root
cause, `expectationsFor()` throwing).

Output: `web/scripts/check-html-locks.mjs`, still green at the 19-route baseline, with the
mechanism in place for 167 routes at batch 1 and 426 at full rollout.

Insert a partition between `Object.keys(manifest.routes)` and the `.map(...)` that builds `PAGES`.
A route whose final path segment carries a file extension is a metadata route, not a page: it has
no `<route>.html` on disk, and `read()` calls `process.exit(1)` on a miss, which today collapses
the whole suite to one failing test carrying `BUILD_HINT` — the most misleading message this file
can produce, because the build succeeded.

Add, above the `PAGES` construction:
  - a predicate that classifies a manifest route as a page or as a metadata route by testing the
    final segment for a dot-extension;
  - `PAGE_ROUTES` and `METADATA_ROUTES`, both derived from the sorted manifest keys;
  - `EXPECTED_METADATA_ROUTES`, a hard-coded literal `Set`, empty today. Phase 5 adds the sitemap
    route string to it in the same change that adds `app/sitemap.js`. Write the reason down: the
    set is what stops the filter becoming a place routes disappear into.

Build `PAGES` from `PAGE_ROUTES` only.

Add one test that makes the partition non-vacuous and correct without depending on the app ever
having a metadata route:
  - the classifier puts a sitemap-shaped and a robots-shaped route on the metadata side and puts
    `/`, `/about-us` and a three-segment location route on the page side;
  - `METADATA_ROUTES` equals `EXPECTED_METADATA_ROUTES` exactly, in both directions, so a metadata
    route arriving without a spec clause is a red build rather than a silently skipped page.

Write the explanation ABOVE the literal, never inside it — this file's structural rule 3. Do not
restate the misleading hint string.
