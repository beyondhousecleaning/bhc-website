# Phase 3 — UI Design Contract

> Visual and interaction contract for Phase 3: Programmatic Location × Service Engine.
> Generated by gsd-ui-researcher. Written **autonomously** — no question was put to Sam and none
> blocks planning. Every choice not settled upstream is recorded in §13 with a one-line rationale,
> and the four items that genuinely need Sam are in §14, each already shipping a working default.

## How to read this

This phase designs **nothing new at the token level and almost nothing new at the component
level.** `docs/design/design-system.md` is locked, `02-UI-SPEC.md` is approved, and both still
bind. The twenty-two components, seven type steps, four weights, band-adjacency rule, `tel:`
budget, focus overrides and copy voice are all inherited **verbatim** and are not restated except
where Phase 3 uses them differently.

What this document adds is the layer Phase 2 explicitly deferred (§9.6: *"Locations index, town
hub and combo (Phase 3)"*): **three templates, one data contract, and the rules that keep ~350
generated pages from reading as ~350 copies of one page.**

Three things make this phase different from Phase 2 and they drive most of what follows:

1. **Scale.** Phase 2 hand-authored eighteen pages. Phase 3 generates ~312 new ones. Anything
   stated as "and then someone writes good copy" is not a contract — §5 and §11 are written as
   *composition rules with measured ceilings* instead.
2. **Partial states are permanent, not transient.** SC-5 mandates batched rollout, so for weeks
   at a time most of the town set will not exist. §12's rule is that **geography is computed over
   the published set only**, which makes "links to a page that isn't built yet" structurally
   impossible rather than something CI catches after the fact.
3. **The URL space is frozen.** D2 preserves 95 live URLs exactly. Every naming decision below is
   downstream of URLs that were chosen by someone else, years ago, in American English. §5's
   answer is that **the slug and the visible noun are different values** — a pattern Phase 2
   already shipped (`post-construction-cleaning` renders as *builders clean* on every page).

Sections §1–§4 are inherited and short. §5 (copy at scale), §9 (the three templates), §11
(content-depth mechanics) and §12 (lock deltas) are the substance.

## 1. Design System

Unchanged from `02-UI-SPEC.md` §1. Reproduced only so this document stands alone:

| Property | Value |
|----------|-------|
| Tool | **none** — `@bhc/design-system`, hand-built, zero-dependency, in this repo |
| Preset | not applicable |
| Component library | **none.** No Radix, no Base UI, no Tailwind, no CSS-in-JS |
| Icon library | **none.** Inline hand-authored SVG, `currentColor`, 20/24 `viewBox` |
| Font | Public Sans (`--bhc-font-body`) · Figtree (`--bhc-font-display`) — 8 self-hosted `woff2` |
| Styling | `bhc-`-prefixed classes in `design-system/styles.css`, values exclusively `var(--bhc-*)` |
| Rendering | **React Server Components only.** Zero first-party client modules today; zero after Phase 3 |

### shadcn gate — resolved from upstream, not asked

`components.json` is absent and the stack is Next.js 16, so the gate fires. It is answered **No**,
for the same three reasons `02-UI-SPEC.md` §1 records: the package must have zero dependencies and
no build step; shadcn components are Radix-backed **client** components and `check-html-locks.mjs`
SC-4g asserts every client module resolves inside `/node_modules/next/`; and a preset would fork
the locked token layer (D-04).

Phase 3 makes that answer *stronger*, not weaker. A single client boundary would now cost ~350
pages of hydration on a marketing site whose entire performance case is that seventeen routes
added **zero** client JavaScript (02-15-SUMMARY: 129.8 KB, unchanged from the one-page scaffold).

`Tool: none`. Registry safety gate: not applicable (§6).

### The inline-SVG accessibility rule still applies

`alt` is not a valid attribute on `<svg>`; it is silently dropped and Lock 7 greps `<img>` only.
Decorative SVG takes `aria-hidden="true" focusable="false"`; a meaningful SVG takes `role="img"` +
`aria-label`. Phase 3 adds no new SVG.

## 2. Spacing Scale

Inherited whole from `02-UI-SPEC.md` §2 — every value a multiple of 4, every value already in
`tokens.css`. Phase 3 introduces **no new spacing value**. The three places it uses the scale in a
way Phase 2 did not:

| Element | Token | Value | Why |
|---|---|---|---|
| TownCard grid gap | `--bhc-space-3` | 12px | Already shipped in `.bhc-town-card__grid`. At 56 cards the tighter gap is the difference between a directory and a scroll |
| Gap between county groups on `/locations` | `--bhc-space-12` | 48px | The same step `Prose` uses above an `h2`; a county heading is an `h2` |
| Separation between two stacked InterlinkBlocks | `--bhc-space-12` | 48px | Plus a `1px solid var(--bhc-line)` rule — §9.5 |

**Fixed dimensions** — unchanged: header 64/72px, StickyCallBar 64px + safe area, minimum touch
target **44 × 44px**, prose measure 68ch. The jump-links row on `/locations` (§9.3) is a run of
links and each one must meet the 44px target: `padding-block: var(--bhc-space-3)` gives 44px at
`--bhc-text-sm`.

**Breakpoints:** `480 / 768 / 1024 / 1280`, `min-width` only. The known pre-existing 900px and
720px deviations in `.bhc-hero__grid` / `.bhc-footer__grid` stay untouched (Phase 5 normalises
them). No Phase 3 CSS may use an undocumented breakpoint.

Exceptions: **none.**

## 3. Typography

Inherited whole from `02-UI-SPEC.md` §3, including the recorded and checker-accepted deviation
(seven fluid steps, four weights — trimming would fork the locked `tokens.css`, D-04). The four
structural roles:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | `--bhc-text-base` — 16px → 17px | 400 | 1.65 |
| Label | `--bhc-text-sm` — 14px → 15px | 400 | 1.35 |
| Heading | `--bhc-text-2xl` — 27px → 31px | 700 | 1.15 |
| Display | `--bhc-text-3xl` — 34px → 44px | 700 | 1.15 |

### Where Phase 3's new surfaces bind to the scale

| Element | Token | Notes |
|---|---|---|
| Combo / hub / index `<h1>` | `--bhc-text-3xl` | From `Hero.heading`. Once per page, nowhere else |
| County group heading on `/locations` | `--bhc-text-2xl` | An `<h2>` inside the band, not a `SectionBand` heading |
| `TownCard` title | `--bhc-text-xl` | Tag-scoped: `h3.bhc-town-card__title` is already 700/`--bhc-text-xl` in shipped CSS |
| `TownCard` meta (`Warwickshire · 6 services`) | `--bhc-text-sm` | `--bhc-ink-muted`, shipped |
| Jump-links row | `--bhc-text-sm` | 600 weight, matching the closed list for `--bhc-weight-semibold` |
| `InterlinkBlock` link label / meta | `--bhc-text-base` / `--bhc-text-sm` | Shipped |

**Never a `<div>` or `<span>` styled at heading size.** That pattern is the live-site bug that
cost 101 of 115 pages their `<h1>`. At ~350 generated pages one templated mistake is ~350
mistakes.

**Outline discipline at scale.** Every generated page is exactly one `<h1>` and a **flat run of
`<h2>`s**, with `<h3>` only inside `Prose`, inside a card, or inside a `<summary>`. No level is
skipped and no level is nested deeper than `h3` — which is also Arbor Trail's one genuinely good
structural habit (teardown: *"Clean, one H1, flat H2s, no nesting deeper than H3"*).

## 4. Color

Inherited whole from `02-UI-SPEC.md` §4. No new token, no new pairing, no new accent role.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--bhc-paper` `#FFFFFF` + `--bhc-paper-warm` `#FBF8F5` | Page surface and the alternating bands |
| Secondary (30%) | `--bhc-paper-tint` `#F5EFE8` (cards, quiet blocks) · `--bhc-ink` `#0B2340` (footer) · `--bhc-navy` `#2064B1` (at most **one** band per page) | Cards, footer, the single CTA band |
| Accent (10%) | `--bhc-action` `#F06C24` · `--bhc-action-hover` `#C2410C` · `--bhc-sponge` `#F78C34` | The closed lists below |
| Destructive | `--bhc-danger` `#B42318` | **Unused.** There is no destructive action anywhere in this phase (§5) |

**Accent reserved for** — the Phase 2 closed lists, unchanged. The two entries Phase 3 actually
exercises for the first time at volume:

- `--bhc-action` as the **hover border** on `TownCard` and `InterlinkBlock` links (shipped rule,
  now on ~56 cards at once). It is a fill/edge, never text.
- `--bhc-action-hover` as **inline link text** inside `Prose`, which on a combo page is the only
  orange most readers will see.

`--bhc-blue` and `--bhc-cyan` remain **unused**. Neither has a safe body-text role (white on blue
4.33:1, white on cyan 2.75:1) and a 350-page template is exactly where a "just this once" cyan
panel becomes 350 contrast failures.

### Two colour rules Phase 3 can break by accident and must not

1. **`ReviewCard` sits on `--bhc-paper-tint`.** A `ReviewRail` inside a `tone="tint"` band renders
   tint cards on a tint ground. Every rail in §9 is therefore banded `paper` or `warm`. This is
   not a preference; it is why the band orders below look the way they do.
2. **`TownCard` and `RatingBadge` set `--bhc-ink` / `--bhc-ink-muted` directly** rather than
   inheriting `currentColor`. Neither may sit on `--bhc-navy` (`--bhc-ink-muted` on navy is
   1.10:1) or on `--bhc-ink`. No template below places either there.

### Band ordering

The rule is unchanged and absolute: **never two identical tones adjacent; never two `navy` bands
on one page; the one navy band is `CTABand`, immediately above the footer.** Per-template
sequences are in §9 and each was checked for adjacency at authoring time.

One thing the rule did not have to cover in Phase 2 and does now: **`InterlinkBlock` is not a
`SectionBand`.** It renders `<section class="bhc-interlink">` with `padding-block:
var(--bhc-space-12)`, its own `.bhc-container`, and **no ground of its own** — so it paints as
`paper`. It carries no `bhc-section--*` class, so the shipped band-order extractor does not see
it and the adjacency lock will not catch a violation involving one.

**Rule: an `InterlinkBlock` counts as a `paper` band for adjacency.** It may not be placed
immediately before or after a `tone="paper"` `SectionBand`. Two InterlinkBlocks may sit back to
back (that is design-system.md §3.5's own layout) and are separated by a hairline — §9.5.

### The slug is not the noun

D2 freezes 95 URLs written in American English. D14 wants UK vocabulary. Both hold at once,
because **the URL segment and the rendered noun are different values** — the pattern
`web/content/services.js` already ships, where `post-construction-cleaning` is written as
*builders clean* in every sentence on the page.

The six combo services, their frozen slugs, and the nouns that appear on screen:

| Combo slug (**frozen — D2**) | `<h1>` noun | `<title>` noun | chars | Sentence-case form used in prose |
|---|---|---|---|---|
| `domestic-cleaning` | Domestic Cleaning | Domestic Cleaning | 17 | domestic cleaning |
| `deep-cleaning` | Deep Cleaning | Deep Cleaning | 13 | deep clean |
| `end-of-tenancy-cleaning` | End of Tenancy Cleaning | End of Tenancy | 14 | end of tenancy clean |
| `apartment-cleaning` | **Flat Cleaning** | **Flat Cleaning** | 13 | flat clean |
| `move-out-cleaning` | Move-Out Cleaning | **Move-Out Clean** | 14 | move-out clean |
| `post-construction-cleaning` | **Builders Clean** | Builders Clean | 14 | builders clean |

`apartment-cleaning` → *Flat Cleaning* is the one genuinely new application of the rule. The word
*apartment* is on `02-UI-SPEC.md` §5's banned-vocabulary list and the acceptance grep for the
content modules looks for it; the slug keeps it, the page never says it.

**The sixth service is `post-construction-cleaning`** (§13-D). The existing 95 URLs carry five
services; the roadmap's arithmetic (56 towns × 6 ≈ 336) requires a sixth. It is not
`move-in-cleaning`, because `move-out-cleaning` and `end-of-tenancy-cleaning` already occupy that
intent twice over (see the cannibalisation note below) and a third would make it three times.
*Builders clean* has the lowest semantic overlap of the remaining candidates, the shortest display
noun (which is what makes titles fit — see the measurement), and a 1,100-word parent service page
already live.

> **A cannibalisation risk the audit did not flag, discovered here.** `move-out-cleaning` and
> `end-of-tenancy-cleaning` both exist for all 19 legacy towns — **38 pages competing for one UK
> intent**, structurally the same defect as `south-coventry`/`coventry-south` at nineteen times the
> scale. D2 forbids redirecting either, so the fix is editorial and it is binding on the content
> layer: **`move-out-cleaning` is written for the owner-occupier leaving a house they own** (no
> deposit, no inventory clerk, no letting agent), and **`end-of-tenancy-cleaning` is written for
> the tenant or landlord with a deposit and a check-out inventory**. Each page's prose must name
> the other and link to it — the sibling-services `InterlinkBlock` already does the linking; the
> prose must do the disambiguating. No shared paragraph may appear on both.

### The `<h1>` deck — this is Success Criterion 4

| Template | `<h1>` pattern | Example (longest in the corpus) |
|---|---|---|
| Locations index | `Areas We Cover` | *Areas We Cover* |
| Town hub | `House Cleaning in {Town}` | *House Cleaning in Stourport-on-Severn* |
| Combo | `{h1 noun} in {Town}` | *End of Tenancy Cleaning in Sutton Coldfield* |

- **No adjective.** Arbor Trail prefixes theirs (*Trusted Move Out Cleaning in Taylor, MI*) and the
  live BHC site's whole `<h1>` catastrophe was adjective fragments. The variety lives in the
  eyebrow, which is decoration and renders as a `<p>`.
- **Combo eyebrow** = the service's shipped Phase 2 eyebrow (`Top to bottom, once`,
  `Get the deposit back`, …). Six strings over ~336 pages is acceptable for three decorative words.
- **Town hub eyebrow** = the town's county (`Warwickshire`, `Shropshire`). One word, true, and the
  only place the county appears above the fold.
- **Locations index** uses `Hero align="centered"` with no image, and its `<h1>` carries neither a
  service nor a town. It joins the utility pages in the set Lock 1's *"contains the service and/or
  town"* clause must be scoped away from (§12, delta 16). `Areas We Cover` is
  `design-system.md` §3.3's own wording and matches the header nav label exactly.
- **No `Hero.image` on any of the three templates.** `image` is optional; the service pages already
  ship without one; and there is no photography (the Canva blocker). ~336 hero images would also
  put an LCP element on every generated page for no content.

> **The `{noun} in {town}` phrase appears in the `<h1>` and in no other heading on the page.**
> This is the direct fix for the one on-page flaw the Arbor Trail teardown identifies —
> *"Duplicate H2s on-page … repeating the exact keyword"*. It is testable and §12 delta 20 tests it.

### Titles and meta descriptions — measured, not patterned

Phase 2 learned this the hard way: its first service-title pattern measured **78 characters**
against a 60-cap and had to be re-derived per page. At ~336 pages per-page authoring is not
available, so the patterns below are **measured against the longest town in the corpus** before
being written down.

Brand suffix ` | Beyond House Cleaning` = **24 characters**. Longest town names in the data set:
`Stratford-upon-Avon` and `Stourport-on-Severn`, **19** characters each.

| Template | Title form | Worst case | Chars |
|---|---|---|---|
| Locations index | `Areas We Cover \| Beyond House Cleaning` | — | **38** |
| Town hub | `Cleaners in {Town} \| Beyond House Cleaning` | Stourport-on-Severn | **55** |
| Combo | `{title noun} in {Town} \| Beyond House Cleaning` | End of Tenancy in Stourport-on-Severn | **61** ✗ |

The town-hub form is `Cleaners in {Town}` rather than `House Cleaning in {Town}` for two reasons
that point the same way: it fits for **every** town with 5 characters to spare, and `cleaner
<town>` is the exact query REQ-organic-visibility names as the map-pack target. The word
*cleaning* is still in the title — it is in the brand.

**The combo form does not fit for every pair, and pretending otherwise is how Phase 2 lost a
day.** Measured, with the §5 title nouns:

| Title noun | chars | Longest town that still fits (≤ 36 for noun + `" in "` + town) | Combo pages that must drop the brand |
|---|---|---|---|
| Deep Cleaning | 13 | 19 | **0** |
| Flat Cleaning | 13 | 19 | **0** |
| End of Tenancy | 14 | 18 | **2** |
| Builders Clean | 14 | 18 | **2** |
| Move-Out Clean | 14 | 18 | **2** |
| Domestic Cleaning | 17 | 15 | **5** |

**Eleven of ~336 titles cannot carry the brand.** The rule is therefore a two-candidate
deterministic chain, not a pattern:

```
title = fits60(`${titleNoun} in ${town} | ${BRAND}`)
      ? `${titleNoun} in ${town} | ${BRAND}`
      : `${titleNoun} in ${town}`          // worst case 37 in this corpus
```

CI asserts three things about it (§12 delta 17), and deliberately **not** a magic count — the
count changes with every batch:

1. every title ≤ 60 characters;
2. every combo and town-hub title contains its town;
3. a title omits the brand suffix **only** where adding it would exceed 60.

Assertion 3 is the one that matters: it makes the fallback provable rather than a place where
titles quietly lose the brand.

**Descriptions.** Phase 2's `describe()` form does not fit a combo page (it hard-codes *across
Warwickshire*). The combo/hub form, measured:

```
Rated 4.9 by 175 Google reviews. {Subject} from DBS-checked, insured local cleaners.
Free quote in two minutes.
```

Fixed length 102. Subject = `{h1 noun} in {Town}`, max 46 (*End of Tenancy Cleaning in
Stourport-on-Severn*), min 22. **Range 124–148, cap 155.** ✓ Every description carries `4.9`,
`175` and `Google`, which SC-4i already asserts on every built page.

Locations index description (measured **141**):

```
Rated 4.9 by 175 Google reviews. House cleaning across Warwickshire, Coventry and the
West Midlands from DBS-checked, insured local cleaners.
```

> **Lock 8's town clause becomes true for the first time.** It reads *"title … contains the town"*.
> Phase 3 is the phase where that is finally satisfiable — on the town-bearing templates. Phase 5
> owns the assertion and must scope it to combo + town hub, or it fails on the thirteen home,
> service and utility pages that are correct without a town, plus `/locations`.

### Voice

Unchanged from `02-UI-SPEC.md` §5: *a genuinely local Warwickshire cleaning team, not a national
booking platform.* Plain UK English (*tenancy*, *flat*, *skirting boards*, *hoover*, *builders
clean*), contractions, concrete nouns, named towns, never *your local area*.

Two rules this phase adds because generation makes them breakable:

- **Never a postcode district in rendered output.** Lock 5 bans full postcodes; PROJECT.md bans
  *targeting* districts. This contract also bans **rendering** them: `B62`, `CV32`, `WV14` never
  appear as a label, a heading, a card meta line or in prose. The named localities from
  `service-area-coverage.md` (Romsley, Hunnington, Hayley Green) are the correct, and much better,
  substitute.
- **No claim whose number is not computed.** The index may not say "56 towns" while 20 are
  published; the town hub may not say "all six services" unless six render. Any number in copy is
  interpolated from the published data or it is not written (§11).

## 7. Component Inventory

**Phase 3 builds zero new components.** All twenty-two exist, ship in the four-file shape, are
registered in both `.design-sync` maps, and are covered by delta 9. This phase writes **data and
three route files**.

Three components built in Phase 2 and used nowhere finally have a consumer:

### 7.1 `TownCard` — first use, at 56 instances

```ts
interface TownCardProps { town: string; href: string; region?: string; serviceCount?: number; headingLevel?: 2|3|4; as?: ElementType; }
```

Shipped and unchanged. Contract for this phase's call sites:

- `town` — the **display** name (`Stourport-on-Severn`, `Sutton Coldfield`). Never a slug, never a
  postcode district, never a full postcode. Both prohibitions are in the component's own header
  comment and Lock 5 scans package source and built HTML.
- `region` — the **county for display** (`Warwickshire`, `Shropshire`, `Oxfordshire`). This is
  **not** the URL region segment; see §8's two-region rule. Banbury renders `Oxfordshire · 6
  services` while its combo URLs live under `/location/warwickshire/`.
- `serviceCount` — **always `6`**, because a town is published with all six combos or not at all
  (§11's atomicity rule). The component's `serviceCount: 0` behaviour (render no count rather than
  "0 services") is a safety net that must never fire in production; if it fires, a town shipped
  half-built.
- `headingLevel` — **`3`**. The county name is the `<h2>`.
- Grid: the shipped `.bhc-town-card__grid` (`repeat(auto-fill, minmax(200px, 1fr))`, gap
  `--bhc-space-3`). At a 1200px container that is five columns; 56 cards is twelve rows across
  seven groups. No card is taller than two lines.

### 7.2 `InterlinkBlock` + `geo.js` — the machinery already exists

`geo.js` ships `distanceMiles`, `nearestTowns` (excludes self, nearest first) and
`buildInterlinks`, with the audited pin distances locked by a test. SC-4's *"computed from
geography, never hand-picked"* is satisfied by **using it**, not by writing anything new.

Two call-site rules:

1. **`nearestTowns` is called with the published town array, never the full one** (§11). This is
   the single line that makes batched rollout safe.
2. **The `meta` on nearby links is the destination town's county, not the distance.** `geo.js`'s
   `buildInterlinks` currently formats `${miles.toFixed(1)} miles away`; that is fine at 1.7 miles
   and actively harmful at 46.2 (Telford), where it advertises how far away we are on a page whose
   entire job is to read as local. The geography stays in the **ordering**, which is where SC-4
   requires it. Implementation: add an optional `metaFor(town, miles)` callback to
   `buildInterlinks` defaulting to today's string — one parameter, backwards compatible, no
   behaviour change for any existing caller (there are none).

### 7.3 `Breadcrumbs` — the trail finally has real parents

Shipped behaviour, verified in source and load-bearing here:

- Only the **last** crumb ever carries `aria-current="page"` (§13-R of Phase 2, fixed in plan

- `item` URLs in the `BreadcrumbList` JSON-LD are resolved with `new URL(href, siteUrl)`, so a data
  row missing a leading slash throws at build rather than serialising a broken URL into schema on

- `.bhc-breadcrumbs__list` is `flex-wrap: wrap` — a four-crumb trail wraps cleanly at 375px.

## 8. Data Contract & the Client Boundary

### 8.1 Zero client components — again

**Phase 3 adds no `use client` directive and no first-party client module.** SC-4g asserts every
module in the client-reference manifest resolves inside `/node_modules/next/`. The two places this
phase would be tempted:

| Temptation | Why it is refused | What ships instead |
|---|---|---|
| A filter/search box on `/locations` (56 towns) | Needs state → client boundary → SC-4g red | A jump-links row of in-page anchors, grouped by county (§9.3). Zero JS, works with JS off, and every group is a real `id` a browser can link to |
| A lazy-loaded static map | Needs IntersectionObserver → client boundary; and a map of the service area is a picture of where the business is (D4) | Nothing. §13-N |

Navigation remains plain `<a href>`, no `next/link`. Accepted cost: no prefetch. Accepted benefit:
the JS budget stays flat as the page count goes 18 → ~350. Every link-bearing component still takes
`as?: ElementType` as the one-line escape hatch.

### 8.2 The towns data file — SC-1

One module, `web/content/towns.js`, in the `site.js` / `services.js` house style (a `.js`, not a
`.jsx`, for the two reasons `site.js`'s header gives). Field contract:

| Field | Type | Rule |
|---|---|---|
| `slug` | string | **Globally unique**, because the hub URL `/locations/<town>` has no region segment. Frozen for the 19 legacy towns |
| `name` | string | The display name. A post town or a named suburb. **Never a postcode district** |
| `urlRegion` | string | The **frozen** first segment of the combo URL. `warwickshire` for all 19 legacy towns whether or not that is true |
| `county` | string | The **display** county. What `TownCard.region`, the hub eyebrow and the index grouping use |
| `lat` / `lon` | number | Town centroid. Feeds `geo.js`. Public data, never rendered |
| `batch` | 1..5 | Rollout batch (§11). Ordered by distance from the Leamington-Spa centroid |
| `localities` | string[] | Named suburbs/villages from `service-area-coverage.md`. The single richest source of genuine per-town content (§10) |

> **`urlRegion` is a legacy string, not a truth claim — and it must never be rendered.** All 95
> live combo URLs sit under `/location/warwickshire/`, including `banbury` (Oxfordshire),
> `daventry` (Northamptonshire), `evesham` (Worcestershire) and `solihull-south` (West Midlands).
> D2 freezes those URLs. If the breadcrumb, the hub eyebrow or the index grouping reads
> `urlRegion`, four towns publish a false county on every one of their pages. **Everything visible
> reads `county`; only the route reads `urlRegion`.**

> **The registered-office coordinates never enter the repo.** Anywhere pin-relative ordering is
> needed — batch order, the service pages' "towns we cover" list — the origin is the
> **`leamington-spa` town centroid**, a public town-centre coordinate 0.8 miles from the pin that
> produces the same ordering. CV32 6EQ's latitude and longitude do not appear in a data file, a
> comment, a test fixture or a commit message. This is D4 applied to a class of data D4's authors
> did not anticipate, and Lock 5's postcode matchers would not catch it.

## 10. Content Depth at 348 Pages

This is where programmatic SEO fails, so this section is a mechanism with measured ceilings rather
than an instruction to write well.

### 10.1 The bar, and where the margin comes from

The audit's finding is that the live site's 95 pages are **safe to scale** — median pairwise 5-gram
Jaccard **0.049** against Arbor Trail's 0.100, 821 median unique words against their 353, and the
town-masked control barely moves the numbers, which is the proof they are not variable
substitution. That margin comes from **depth**, and it evaporates if the new towns ship thin pages.

### 10.2 What is templated and what varies — explicitly

A combo page's body is a fixed sequence of blocks, each drawing from a **different axis**. This is
the whole design:

| Block | Words | Axis | Distinct variants | Repeats across |
|---|---|---|---|---|
| Hero lead | ~35 | town × service | 58 × 6 assembled | — |
| Opening prose (`h2` + 2 `p`) | ~170 | **town** | 58 authored profiles | that town's 6 pages |
| Service detail (`h2` + `p` + `ul`) | ~300 | **service**, ×4 variants | 6 × 4 = 24 authored | ~14 towns each |
| Housing-stock angle (`h3` + `p`) | ~220 | **town type × service** | 6 types × 6 services = 36 | towns of one type |
| Local coverage (`h2` + `p`) | ~90 | **town** — from `localities` | 58, factual | that town's 6 pages |
| "What's included" | ~150 | **service** | 6 | 58 towns each |
| **Total** | **~965** | | | |

Authoring cost: ~58 town profiles + 24 service variants + 36 type×service blocks + 58 locality
paragraphs ≈ **22,000 words**, against the ~280,000 that hand-writing 348 pages would need. Every
one of those fragments is real prose written once; **none is a sentence with a `{town}` hole in
it.**

**Three prohibitions on the composition layer:**

1. **No sentence may be produced by substituting a town name into an otherwise fixed sentence.**
   The town appears in the `<h1>`, the lead, the locality paragraph and the interlink headings —
   places where a proper noun belongs — and the prose is *selected*, not *filled*.
2. **The `move-out-cleaning` and `end-of-tenancy-cleaning` fragment pools share nothing.** §5's
   cannibalisation note; 38 pages depend on it.
3. **`localities` are rendered as place names only.** Never the district code they came from.

### 10.3 The measured ceilings — CI, not aspiration

Same method as the audit (§12 of `seo-audit-2026-08-06.md`), run over built HTML: strip
`<script>`/`<style>`/`<nav>`, drop sentences appearing on >30% of pages, then 5-gram shingle
Jaccard over the remaining body text.

| Assertion | Threshold | Basis |
|---|---|---|
| Unique body words per **combo** page | **≥ 800** | Lock 11 / SC-4 / REQ-content-depth-bar |
| Unique body words per **town hub** | ≥ 600 | The live hub is 670; a hub is a signpost |
| Unique body words on **`/locations`** | ≥ 300 | It is an index |
| All-pairs median Jaccard | **≤ 0.06** | Live site 0.049. Never worse than the thing we are scaling |
| Within-service, across-towns median | **≤ 0.10** | Arbor Trail's overall median. Never worse than the competitor |
| **Worst pair, any two combo pages** | **≤ 0.35** | Phase 2's service pages measured 0.327; hold what already ships, not the 0.6 ceiling |
| Town-masked delta on the medians | **≤ ±0.02** | **The anti-mad-libs gate.** If pages were variable substitution, masking the town would collapse them toward identity and this moves a lot |

The word count is measured over the page's **authored prose only**: `<main>` text minus header,
footer, breadcrumb, review quotes, ProcessSteps bodies, FAQ answers and interlink labels. Review
text is shared across ~56 pages and FAQ answers across ~58; counting either toward "unique body
words" would let the bar be met without writing anything.

Cost: 348 pages is 60,378 pairs. Shingle sets over ~950 words each is a few seconds in node. If it
ever exceeds 60s in CI, the within-service cohorts (6 × C(58,2) = 9,918 pairs) run exhaustively and
the cross-service population samples at 10% — never the reverse, because the within-service cohort
is the one that can actually collide.

### 10.4 Reviews on generated pages

**Three cards on every combo page and every town hub**, in a `warm` band, matching the service
pages. Not six: these pages already carry ~950 words plus a photo band.

**Which three varies by town.** `reviews.js` gains `reviewsForCombo(townSlug, serviceSlug)` — the
service's ordered candidate list, rotated by the town's index — so the trio leads with the review
that names the job while ~336 pages do not all quote the same three customers. Deterministic, so
the build is reproducible.

Two hard constraints inherited from plan 02-16 and not negotiable:

- **No review carries a town, and none may be invented one.** `ReviewRail`'s `town` prop, which
  narrows its own heading, **is not used**. The heading is `What our customers say` everywhere
  (§5). Phase 4 SC-3's "town-filtered reviews … where available" is satisfied by *where available*
  being nowhere until real town data exists.
- The 320-character data-layer cap holds, met by **selection, not truncation**.

### 10.5 Photography

Every combo and hub page renders `BeforeAfterSlider` with **no `pairs`**, emitting
`data-bhc-photo-state="pending"`. Delta 8 currently asserts the marker on exactly seven routes and
zero elsewhere; Phase 3 grows that to a per-template rule (§12 delta 21). This is SC-3's whole
point: **no page is ever blocked on the Canva pull**, and the marker stays the machine-readable
hand-off to Phase 4.

The town hub does **not** carry a slider (`design-system.md` §3.4 does not list one, and a
photo band on 58 signpost pages is weight without content).

## 11. Batching, Publication and Partial States — SC-5

### 11.1 One flag, and everything derives from it

`towns.js` carries `batch: 1..5`; one constant, `PUBLISHED_BATCHES`, gates it; `PUBLISHED_TOWNS`
is the single filtered array. **Every derived list reads `PUBLISHED_TOWNS` and nothing reads the
raw array:**

- `generateStaticParams` for `/locations/[town]` and `/location/[region]/[town]/[service]`
- `nearestTowns()` — both the combo and hub interlinks
- the `/locations` grid and its county groups and jump links
- the home page's locations teaser
- the service pages' "towns we cover" block
- the sitemap

This is what makes "a town hub linking to a combo page that isn't built yet" **structurally
impossible** rather than something delta 6 catches after the fact. Delta 6 stays green by
construction, and it stays a real assertion because nothing is exempted from it.

**Atomicity: a town publishes with all six of its combo pages, or it does not publish.** There is
no half-published town, which is why `TownCard.serviceCount` is always `6` and why no template
needs a "some services coming to this town" state.

### 11.2 The batches

Batch order is ascending distance from the `leamington-spa` centroid — the map-pack-contestable

### 11.3 Partial states must never look broken — the rules that make it so

| Risk | Rule |
|---|---|
| The index claims 58 towns while 20 are live | **No number in copy that is not interpolated from `PUBLISHED_TOWNS`.** The `<h1>` is `Areas We Cover` — no count. The intro names only counties with ≥1 published town |
| A county group renders empty | A county with zero published towns produces **no group and no jump link**. The groups are derived, not enumerated |
| "Nearest towns" points at an unbuilt town | `nearestTowns(town, PUBLISHED_TOWNS, n)` |
| A hub's ServiceCard 404s | Atomicity (§11.1) |
| Fewer than `n` nearby towns exist early in the rollout | `nearestTowns` returns what it has; `InterlinkBlock` renders the shorter list. It returns `null` only at zero, and zero is impossible from batch 1 (20 towns) |
| The header gains an "Areas We Cover" item before `/locations` exists | The nav item and the route land in the **same** change. Delta 6 would catch it, but this is cheaper than a red build |
| A published set of zero | **Build failure**, deliberately. `assert(PUBLISHED_TOWNS.length > 0)` in `towns.js` at module load. There is no empty-index rendered state and no "coming soon" copy anywhere (Phase 1's debt-marker record stands) |

Later batches change earlier pages' nearby lists. That is correct — the links are computed, and
recomputation is the property that makes them un-rottable. It also gives Phase 5's `<lastmod>` real
values to publish.
