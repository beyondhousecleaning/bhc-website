# Phase 3 — UI Design Contract

> Visual and interaction contract for Phase 3: Programmatic Location × Service Engine.
> Generated by gsd-ui-researcher. Written **autonomously** — no question was put to Sam and none
> blocks planning. Every choice not settled upstream is recorded in §13 with a one-line rationale,
> and the four items that genuinely need Sam are in §14, each already shipping a working default.

## How to read this

This phase designs **nothing new at the token level and almost nothing new at the component
level.** `docs/design/design-system.md` is locked, `02-UI-SPEC.md` is approved, and both still
bind. The twenty-two components, seven type steps, four weights, band-adjacency rule, `tel:`
budget, focus overrides and copy voice are all inherited **verbatim** and are not restated except
where Phase 3 uses them differently.

What this document adds is the layer Phase 2 explicitly deferred (§9.6: *"Locations index, town
hub and combo (Phase 3)"*): **three templates, one data contract, and the rules that keep 406
generated pages from reading as 406 copies of one page.**

Three things make this phase different from Phase 2 and they drive most of what follows:

1. **Scale.** Phase 2 hand-authored eighteen pages. Phase 3 generates **317** new ones. Anything
   stated as "and then someone writes good copy" is not a contract — §5 and §11 are written as
   *composition rules with measured ceilings* instead.
2. **Partial states are permanent, not transient.** SC-5 mandates batched rollout, so for weeks
   at a time most of the town set will not exist. §12's rule is that **geography is computed over
   the published set only**, which makes "links to a page that isn't built yet" structurally
   impossible rather than something CI catches after the fact.
3. **The URL space is frozen.** D2 preserves 95 live URLs exactly. Every naming decision below is
   downstream of URLs that were chosen by someone else, years ago, in American English. §5's
   answer is that **the slug and the visible noun are different values** — a pattern Phase 2
   already shipped (`post-construction-cleaning` renders as *builders clean* on every page).

Sections §1–§4 are inherited and short. §5 (copy at scale), §9 (the three templates), §11
(content-depth mechanics) and §12 (lock deltas) are the substance.

### shadcn gate — resolved from upstream, not asked

`components.json` is absent and the stack is Next.js 16, so the gate fires. It is answered **No**,
for the same three reasons `02-UI-SPEC.md` §1 records: the package must have zero dependencies and
no build step; shadcn components are Radix-backed **client** components and `check-html-locks.mjs`
SC-4g asserts every client module resolves inside `/node_modules/next/`; and a preset would fork
the locked token layer (D-04).

Phase 3 makes that answer *stronger*, not weaker. A single client boundary would now cost 426
routes' worth of hydration on a marketing site whose entire performance case is that seventeen routes
added **zero** client JavaScript (02-15-SUMMARY: 129.8 KB, unchanged from the one-page scaffold).

`Tool: none`. Registry safety gate: not applicable (§6).

### The inline-SVG accessibility rule still applies

`alt` is not a valid attribute on `<svg>`; it is silently dropped and Lock 7 greps `<img>` only.
Decorative SVG takes `aria-hidden="true" focusable="false"`; a meaningful SVG takes `role="img"` +
`aria-label`. Phase 3 adds no new SVG.

## 2. Spacing Scale

Inherited whole from `02-UI-SPEC.md` §2 — every value a multiple of 4, every value already in
`tokens.css`. Phase 3 introduces **no new spacing value**, and it declares touch targets the way
the shipped CSS already does — `min-height: 44px`, the idiom used in all six existing cases.
**Padding alone does not reach it**: `padding-block: var(--bhc-space-3)` on `--bhc-text-sm`
computes to 12 + 12 + (14 × 1.35) = **42.9px** at the mobile end of the clamp, which is under the
target and looks like it is over it. The three places Phase 3 uses the scale in a way Phase 2 did
not:

| Element | Token | Value | Why |
|---|---|---|---|
| TownCard grid gap | `--bhc-space-3` | 12px | Already shipped in `.bhc-town-card__grid`. At 58 cards the tighter gap is the difference between a directory and a scroll |
| Gap between county groups on `/locations` | `--bhc-space-12` | 48px | The same step `Prose` uses above an `h2`; a county heading is an `h2` |
| Separation between two stacked InterlinkBlocks | `--bhc-space-12` | 48px | Plus a `1px solid var(--bhc-line)` rule — §9.5 |

**Fixed dimensions** — unchanged: header 64/72px, StickyCallBar 64px + safe area, minimum touch
target **44 × 44px**, prose measure 68ch. Both new link classes in §7.5 — the jump-links row and
the per-group back link on `/locations` — declare it as `min-height: 44px`, not as padding.

**Breakpoints:** `480 / 768 / 1024 / 1280`, `min-width` only. The known pre-existing 900px and
720px deviations in `.bhc-hero__grid` / `.bhc-footer__grid` stay untouched (Phase 5 normalises
them). No Phase 3 CSS may use an undocumented breakpoint.

Exceptions: **none.**

| Heading | `--bhc-text-2xl` — 27px → 31px | 700 | 1.15 |
| Display | `--bhc-text-3xl` — 34px → 44px | 700 | 1.15 |

### Where Phase 3's new surfaces bind to the scale

| Element | Token | Notes |
|---|---|---|
| Combo / hub / index `<h1>` | `--bhc-text-3xl` | From `Hero.heading`. Once per page, nowhere else |
| County group heading on `/locations` | `--bhc-text-2xl` | An `<h2>` inside the band, not a `SectionBand` heading |
| `TownCard` title | `--bhc-text-xl` | Tag-scoped: `h3.bhc-town-card__title` is already 700/`--bhc-text-xl` in shipped CSS |
| `TownCard` meta (`Warwickshire · 6 services`) | `--bhc-text-sm` | `--bhc-ink-muted`, shipped |
| Jump-links row | `--bhc-text-sm` | 600 weight, matching the closed list for `--bhc-weight-semibold` |
| `InterlinkBlock` link label / meta | `--bhc-text-base` / `--bhc-text-sm` | Shipped |

**Never a `<div>` or `<span>` styled at heading size.** That pattern is the live-site bug that
cost 101 of 115 pages their `<h1>`. At 406 generated pages one templated mistake is 406
mistakes.

**Outline discipline at scale.** Every generated page is exactly one `<h1>` and a **flat run of
`<h2>`s**, with `<h3>` only inside `Prose`, inside a card, or inside a `<summary>`. No level is
skipped and no level is nested deeper than `h3` — which is also Arbor Trail's one genuinely good
structural habit (teardown: *"Clean, one H1, flat H2s, no nesting deeper than H3"*).

## 4. Color

Inherited whole from `02-UI-SPEC.md` §4. No new token, no new pairing, no new accent role.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--bhc-paper` `#FFFFFF` + `--bhc-paper-warm` `#FBF8F5` | Page surface and the alternating bands |
| Secondary (30%) | `--bhc-paper-tint` `#F5EFE8` (cards, quiet blocks) · `--bhc-ink` `#0B2340` (footer) · `--bhc-navy` `#2064B1` (at most **one** band per page) | Cards, footer, the single CTA band |
| Accent (10%) | `--bhc-action` `#F06C24` · `--bhc-action-hover` `#C2410C` · `--bhc-sponge` `#F78C34` | The closed lists below |
| Destructive | `--bhc-danger` `#B42318` | **Unused.** There is no destructive action anywhere in this phase (§5) |

**Accent reserved for** — the Phase 2 closed lists, unchanged. The two entries Phase 3 actually
exercises for the first time at volume:

- `--bhc-action` as the **hover border** on `TownCard` and `InterlinkBlock` links (shipped rule,
  now on 58 cards at once). It is a fill/edge, never text.
- `--bhc-action-hover` as **inline link text** inside `Prose`, which on a combo page is the only
  orange most readers will see.

`--bhc-blue` and `--bhc-cyan` remain **unused**. Neither has a safe body-text role (white on blue
4.33:1, white on cyan 2.75:1) and a 350-page template is exactly where a "just this once" cyan
panel becomes 350 contrast failures.

### Two colour rules Phase 3 can break by accident and must not

1. **`ReviewCard` sits on `--bhc-paper-tint`.** A `ReviewRail` inside a `tone="tint"` band renders
   tint cards on a tint ground. Every rail in §9 is therefore banded `paper` or `warm`. This is
   not a preference; it is why the band orders below look the way they do.
2. **`TownCard` and `RatingBadge` set `--bhc-ink` / `--bhc-ink-muted` directly** rather than
   inheriting `currentColor`. Neither may sit on `--bhc-navy` (`--bhc-ink-muted` on navy is
   1.10:1) or on `--bhc-ink`. No template below places either there.

### Band ordering

The rule is unchanged and absolute: **never two identical tones adjacent; never two `navy` bands
on one page; the one navy band is `CTABand`, immediately above the footer.** Per-template
sequences are in §9 and each was checked for adjacency at authoring time.

One thing the rule did not have to cover in Phase 2 and does now: **`InterlinkBlock` is not a
`SectionBand`.** It renders `<section class="bhc-interlink">` with `padding-block:
var(--bhc-space-12)`, its own `.bhc-container`, and **no ground of its own** — so it paints as
`paper`. It carries no `bhc-section--*` class, so the shipped band-order extractor does not see
it and the adjacency lock will not catch a violation involving one.

**Rule: an `InterlinkBlock` counts as a `paper` band for adjacency.** It may not be placed
immediately before or after a `tone="paper"` `SectionBand`. Two InterlinkBlocks may sit back to
back (that is design-system.md §3.5's own layout) and are separated by a hairline — §9.5.

> **This breaks eight pages that ship today, and Phase 3 is what breaks them.** Measured in
> `web/app/page.jsx` and `web/app/services/[service]/page.jsx`, both end
> `tint (ProcessSteps) → warm (ReviewRail) → paper (FAQAccordion) → navy (CTABand)`. Delta 16
> requires an InterlinkBlock on Home and on every service page, and the only slot for it — after
> the rail, before the FAQ, which is where `design-system.md` §3.2 and §3.1 both put it — lands a
> `paper` interlink immediately above a `paper` FAQ band.
>
> **Fix: the FAQ band on Home and all seven service pages moves `paper` → `tint`**, giving
> `warm → paper (interlink) → tint → navy`. That is exactly what §9.4 and §9.5 already specify for
> the new templates; the eight existing pages simply have to be brought into line in the same
> change. One prop per file. Delta 27 catches it if it is forgotten, but a lock that fires on eight
> pages the moment the phase's headline feature lands is a poor way to find out.

### The slug is not the noun — and the concept is neither

D2 freezes 95 URLs written in American English. D14 wants UK vocabulary. Both hold at once,
because **the URL segment and the rendered noun are different values** — the pattern
`web/content/services.js` already ships, where `post-construction-cleaning` is written as
*builders clean* in its crumb, its nav label and every sentence of its prose.

Phase 2 shipped that pattern **incompletely**: `services.js:874` still sets
`h1: 'Post-Construction Cleaning in ${AREA_LONG}'`, and `standard-home-cleaning`'s `<h1>` is
*Regular House Cleaning* while its concept is *domestic cleaning*. As it stands the same concept
would ship two different nouns depending on which template you land on. **One concept, one noun,
every template** — the table below is the single source, and four `services.js` records are
corrected in this phase.

**The correction is to `h1`, `crumb` and `title`, not to `h1` alone.** Measured in source, the
disagreements are wider than the heading:

| Record | `h1` | `crumb` | `title` subject |
|---|---|---|---|
| `standard-home-cleaning` → `domestic-cleaning` | Regular House Cleaning → **Domestic Cleaning** | Regular House Cleaning → **Domestic Cleaning** | Regular Cleaning → **Domestic Cleaning** |
| `move-out-cleaning` → `end-of-tenancy-cleaning` | Move-Out Cleaning → **End of Tenancy Cleaning** | Move-Out Cleaning → **End of Tenancy Cleaning** | Move-Out Cleaning → **End of Tenancy** |
| `short-term-rental-cleaning` | Short-Term Rental Cleaning → **Holiday Let Cleaning** | Short-Term Rental Cleaning → **Holiday Let Cleaning** | Rental Cleaning → **Holiday Lets** |
| `post-construction-cleaning` | Post-Construction Cleaning → **Builders Clean** | already correct | already correct |

`services.js`'s own header states that each `crumb` "matches the `nav.js` label exactly", so
**`nav.js`'s `NAV` children and `FOOTER_COLUMNS` Services labels change with them** — plus a
seventh entry each for `/services/apartment-cleaning`. Leave the crumbs alone and one-concept-one-noun
ships broken in the breadcrumb, which is the one place a reader sees the taxonomy as a taxonomy.

  (§12 delta 16).
- **`short-term-rental-cleaning` gains 40 combos**, which is what gives its existing service page
  real destinations for the first time.

| Town group | Count | The six combo services |
|---|---|---|

`TownCard.serviceCount` stays a constant and §11's atomicity rule stays simple.

> ### The intent-duplication defect, and why the new towns do not inherit it
>
> `move-out-cleaning` and `end-of-tenancy-cleaning` are **one UK query intent**. The audit says so
> outright (§6, lines 513-514): *"'domestic cleaning' and 'end of tenancy cleaning' are the
> standard UK terms. `standard-home-cleaning` and `move-out-cleaning` are Americanisms."* b3
> prefers `end-of-tenancy-cleaning`, and §14-1's shipped default 301s the *service* page
> accordingly.
>
> Both already exist as combos on all 18 legacy towns — **36 pages competing for one intent**.
> **D2 freezes those. It does not require creating 40 more.** Shipping this service to the new
> towns would take the defect to 116 pages, and once indexed, D2's own preserve-the-URL logic
> would protect them. That is the one genuinely irreversible decision available in this phase, and
> it is refused.
>
> An earlier draft of this contract proposed resolving the overlap **editorially** — writing
> `move-out` for the owner-occupier and `end-of-tenancy` for the tenant with a deposit. That copy
> distinction is real and it still applies to the 36 frozen pages, but it is **not** a resolution:
> two textually dissimilar pages can still be intent-identical, and delta 23 measures text, so it
> would report green on exactly the problem it was invoked to solve. The structural fix is not
> creating the pages.
>
> **Consequence recorded honestly:** the 18 legacy Warwickshire towns carry no
> `short-term-rental` combo, so Stratford-upon-Avon — a genuine holiday-let market — is served for
> that job only by the region-wide `/services/short-term-rental-cleaning` page. Adding it to the
> legacy towns later is **additive as far as D2 is concerned**: 18 new URLs, no redirect, no
> preserved-URL exposure.
>
> It is **not** free against two invariants this document sets, and both are written to be
> relaxed rather than to forbid it:
>
> - §7.1's *"`serviceCount` is always 6"* becomes *"`serviceCount` is the length of that town's
>   own service list"* — which is what `TownCard` already accepts, and the constant is a
>   convenience, not a contract.
> - §11.1's atomicity rule (*"all six of its combo pages, or it does not publish"*) is about a
>   town's **first** publication. Adding a seventh service to an already-published town is a
>   second, independent atomic unit: all 18 or none, so no town ends up with a service its
>   neighbours lack.
>
> Neither is a prohibition. A later batch that reads them as one has misread them.


### The `<h1>` deck — this is Success Criterion 4

| Template | `<h1>` pattern | Example (longest in the corpus) |
|---|---|---|
| Locations index | `Areas We Cover` | *Areas We Cover* |
| Town hub | `House Cleaning in {Town}` | *House Cleaning in Stourport-on-Severn* |
| Combo | `{h1 noun} in {Town}` | *End of Tenancy Cleaning in Sutton Coldfield* |

- **No adjective.** Arbor Trail prefixes theirs (*Trusted Move Out Cleaning in Taylor, MI*) and the
  live BHC site's whole `<h1>` catastrophe was adjective fragments. The variety lives in the
  eyebrow, which is decoration and renders as a `<p>`.
- **Combo eyebrow** — one per combo service. Five come across from `services.js`; **two must be
  authored**, because the rename leaves two concepts without one. `apartment-cleaning` has never
  had a service record, and `move-out`'s *Get the deposit back* migrates with the record it sits in
  to `end-of-tenancy`, leaving the `move-out` concept — 18 combo pages, no `services.js` record —
  with nothing:

  | Combo service | Eyebrow | Source |
  |---|---|---|
  | `domestic-cleaning` | Weekly or fortnightly | `services.js`, migrates with the rename |
  | `deep-cleaning` | Top to bottom, once | `services.js`, unchanged |
  | `end-of-tenancy-cleaning` | Get the deposit back | `services.js`, migrates with the rename |
  | `post-construction-cleaning` | After the builders leave | `services.js`, unchanged |
  | `short-term-rental-cleaning` | Guest-ready between stays | `services.js`, unchanged |
  | `apartment-cleaning` | **Flats and maisonettes** | **authored here** |
  | `move-out-cleaning` | **Before you hand over the keys** | **authored here** — and deliberately not a deposit line, which now belongs to end-of-tenancy |

  Seven strings over 348 pages is acceptable for three decorative words.

> **Combo metadata does not live in `services.js`, and this is why.** Two of the seven combo
> services have no service-page record — `move-out` (18 combo pages, no page) — while
> `move-in-cleaning` has a record and no combos. Reading combo copy out of `services.js` therefore
> has no home for one and a dead entry for the other. **The seven combo services are their own
> table**, `COMBO_SERVICES` in `web/content/towns.js`, keyed by combo slug and carrying the display
> noun, the title noun, the eyebrow, the description subject and an optional `servicePage` href.
> `services.js` keeps the seven service-page records. The two tables agree on nouns because both
> read §5's concept table, and a module-load guard asserts it — the `reviewsForService` idiom.
- **Town hub eyebrow** = the town's county (`Warwickshire`, `Shropshire`). One word, true, and the
  only place the county appears above the fold.
- **Locations index** uses `Hero align="centered"` with no image, and its `<h1>` carries neither a
  service nor a town. It joins the utility pages in the set Lock 1's *"contains the service and/or
  town"* clause must be scoped away from (§12, delta **18**). `Areas We Cover` is
  `design-system.md` §3.3's own wording and matches the header nav label exactly.
- **No `Hero.image` on any of the three templates.** `image` is optional; the service pages already
  ship without one; and there is no photography (the Canva blocker). 348 hero images would also
  put an LCP element on every generated page for no content.

> **The `{noun} in {town}` phrase appears in the `<h1>` and in no other heading on the page.**
> This is the direct fix for the one on-page flaw the Arbor Trail teardown identifies —
> *"Duplicate H2s on-page … repeating the exact keyword"*. It is testable and §12 delta 20 tests it.

### Titles and meta descriptions — measured, not patterned

Phase 2 learned this the hard way: its first service-title pattern measured **78 characters**
against a 60-cap and had to be re-derived per page. At 348 combo pages per-page authoring is not
available, so the patterns below are **measured against the longest town in the corpus** before
being written down.

Brand suffix ` | Beyond House Cleaning` = **24 characters**. Longest town names:
`Stratford-upon-Avon` and `Stourport-on-Severn`, **19** characters each.

| Template | Title form | Worst case | Chars |
|---|---|---|---|
| Locations index | `Areas We Cover \| Beyond House Cleaning` | — | **38** |
| Town hub | `Cleaners in {Town} \| Beyond House Cleaning` | Stourport-on-Severn | **55** |
| Service page | `{title noun} in Warwickshire \| Beyond House Cleaning` | Domestic Cleaning | **57** |
| Combo | `{title noun} in {Town} \| Beyond House Cleaning` | Domestic Cleaning in Stratford-upon-Avon | **64** ✗ |

The town-hub form is `Cleaners in {Town}` rather than `House Cleaning in {Town}` for two reasons
that point the same way: it fits for **every** town with 5 characters to spare, and `cleaner
<town>` is the exact query REQ-organic-visibility names as the map-pack target. The word
*cleaning* is still in the title — it is in the brand. The same trick lets three combo title nouns
drop their trailing *Cleaning* (`End of Tenancy`, `Move-Out Clean`, `Holiday Lets`).

**The combo form does not fit for every pair, and pretending otherwise is how Phase 2 lost a
day.** Measured over the real 58-town corpus and the per-town service sets above:

| Title noun | chars | Longest town that still fits (≤ 36 for noun + `" in "` + town) | Pages | Must drop the brand |
|---|---|---|---|---|
| Deep Cleaning | 13 | 19 | 58 | **0** |
| Flat Cleaning | 13 | 19 | 58 | **0** |
| Holiday Lets | 12 | 20 | 40 | **0** |
| End of Tenancy | 14 | 18 | 58 | **2** |
| Builders Clean | 14 | 18 | 58 | **2** |
| Move-Out Clean | 14 | 18 | 18 | **1** |
| Domestic Cleaning | 17 | 15 | 58 | **5** |
| | | | **348** | **10** |

**Ten of 348 titles cannot carry the brand.** The rule is therefore a two-candidate deterministic
chain, not a pattern:

```
title = fits60(`${titleNoun} in ${town} | ${BRAND}`)
      ? `${titleNoun} in ${town} | ${BRAND}`
      : `${titleNoun} in ${town}`     // worst case 40: "Domestic Cleaning in Stratford-upon-Avon"
```

CI asserts three things about it (§12 delta 17), and deliberately **not** a magic count — the
count changes with every batch:

1. every title ≤ 60 characters;
2. every combo and town-hub title contains its town;
3. a title omits the brand suffix **only** where adding it would exceed 60.

Assertion 3 is the one that matters: it makes the fallback provable rather than a place where
titles quietly lose the brand.

**Descriptions.** Phase 2's `describe()` form does not fit a combo page (it hard-codes *across
Warwickshire*). The combo/hub form, measured:

```
Rated 4.9 by 175 Google reviews. {Subject} from DBS-checked, insured local cleaners.
Free quote in two minutes.
```

Fixed length 102. Subject = `{display noun} in {Town}` — the **h1** noun, not the title noun, so
the description carries the full term the title had to abbreviate. Max 46 (*End of Tenancy
Cleaning in Stratford-upon-Avon*), min 22. **Range 124–148, cap 155.** ✓ Every description carries
`4.9`, `175` and `Google`, which SC-4i already asserts on every built page.

Locations index description (measured **141**):

```
Rated 4.9 by 175 Google reviews. House cleaning across Warwickshire, Coventry and the
West Midlands from DBS-checked, insured local cleaners.
```

> **Lock 8's town clause becomes true for the first time.** It reads *"title … contains the town"*.
> Phase 3 is the phase where that is finally satisfiable — on the town-bearing templates. Phase 5
> owns the assertion and must scope it to combo + town hub, or it fails on the home,
> service and utility pages that are correct without a town, plus `/locations` and `/_not-found`.

### 7.1 `TownCard` — first use, at 58 instances

```ts
interface TownCardProps { town: string; href: string; region?: string; serviceCount?: number; headingLevel?: 2|3|4; as?: ElementType; }
```

Shipped and unchanged. Contract for this phase's call sites:

- `town` — the **display** name (`Stourport-on-Severn`, `Sutton Coldfield`). Never a slug, never a
  postcode district, never a full postcode. Both prohibitions are in the component's own header
  comment and Lock 5 scans package source and built HTML.
- `region` — the **county for display** (`Warwickshire`, `Shropshire`, `Oxfordshire`). This is
  **not** the URL region segment; see §8's two-region rule. Banbury renders `Oxfordshire · 6
  services` while its combo URLs live under `/location/warwickshire/`.
- `serviceCount` — **always `6`**, because a town is published with all six combos or not at all
  (§11's atomicity rule). The component's `serviceCount: 0` behaviour (render no count rather than
  "0 services") is a safety net that must never fire in production; if it fires, a town shipped
  half-built.
- `headingLevel` — **`3`**. The county name is the `<h2>`.
- Grid: the shipped `.bhc-town-card__grid` (`repeat(auto-fill, minmax(200px, 1fr))`, gap
  `--bhc-space-3`). At a 1200px container that is five columns; 58 cards is twelve rows across
  seven groups. No card is taller than two lines.

### 7.2 `InterlinkBlock` + `geo.js` — the machinery already exists

`geo.js` ships `distanceMiles`, `nearestTowns` (excludes self, nearest first) and
`buildInterlinks`, with the audited pin distances locked by a test. SC-4's *"computed from
geography, never hand-picked"* is satisfied by **using it**, not by writing anything new.

Two call-site rules:

1. **`nearestTowns` is called with the published town array, never the full one** (§11). This is
   the single line that makes batched rollout safe.
2. **`buildInterlinks` reads `town.region` as the URL segment — which `towns.js` calls
   `urlRegion`.** `geo.js` builds `/location/${town.region}/${town.slug}/${s.slug}`, while
   `TownCard.region` is the **display county**. The two props share a name and mean opposite
   things, and a `towns.js` row passed straight in yields `/location/undefined/...` on every link —
   which delta 6 catches, but only after 406 pages of interlinks have been generated wrong.
   **Every `geo.js` call site maps explicitly**, `{ ...town, region: town.urlRegion }`. Section 8.2's
   two-region rule is the reason; this is the one line where it is easy to lose.
3. **The `meta` on nearby links is the destination town's county, not the distance.** `geo.js`'s
   `buildInterlinks` currently formats `${miles.toFixed(1)} miles away`; that is fine at 1.7 miles
   and actively harmful at 46.2 (Telford), where it advertises how far away we are on a page whose
   entire job is to read as local. The geography stays in the **ordering**, which is where SC-4
   requires it. Implementation: add an optional `metaFor(town, miles)` callback to
   `buildInterlinks` defaulting to today's string — one parameter, backwards compatible, no
   behaviour change for any existing caller (there are none).

| Field | Type | Rule |
|---|---|---|
| `slug` | string | **Globally unique**, because the hub URL `/locations/<town>` has no region segment. Frozen for the 19 legacy towns |

> **The registered-office coordinates never enter the repo.** Anywhere pin-relative ordering is
> needed — batch order, the service pages' "towns we cover" list — the origin is the
> **`leamington-spa` town centroid**, a public town-centre coordinate 0.8 miles from the pin that
> produces the same ordering. CV32 6EQ's latitude and longitude do not appear in a data file, a

## 10. Content Depth at 348 Pages

This is where programmatic SEO fails, so this section is a mechanism with measured ceilings rather
than an instruction to write well.

### 10.1 The bar, and where the margin comes from

The audit's finding is that the live site's 95 pages are **safe to scale** — median pairwise 5-gram
Jaccard **0.049** against Arbor Trail's 0.100, 821 median unique words against their 353, and the
town-masked control barely moves the numbers, which is the proof they are not variable
substitution. That margin comes from **depth**, and it evaporates if the new towns ship thin pages.

### 10.2 What is templated and what varies — with the arithmetic published

A combo page's body is a fixed sequence of blocks, each drawing from a **different axis**. The
column that matters is the last one: what a pair of pages actually shares.

| # | Block | Words | Axis | Authored fragments | Shared with a same-service, different-town page |
|---|---|---|---|---|---|
| 1 | Hero lead | 35 | town × service | assembled | never |
| 2 | Opening prose (`h2` + 2 `p`) — the town's own character, incl. its housing stock | 180 | **town** | 58 | never |
| 3 | Service detail (`h2` + `p` + `ul`) | 300 | **service × variant `a`** | 7 × 8 = 56 | iff same `a` — p ≈ 1/8 |
| 4 | How the job runs (`h3` + `p`) | 260 | **service × variant `b`** | 7 × 8 = 56 | iff same `b` — p ≈ 1/8 |
| 5 | County note (`p`) | 90 | **service × county** | **45** — 5 sitewide services × 7 counties, plus `move-out` × the 5 counties its 18 towns span and `short-term-rental` × the 5 its 40 towns span | iff same county — p = 0.240 |
| 6 | Local coverage (`h2` + `p`), from `localities` | 130 | **town**, factual | 58 | never |
| | **Counted prose** | **995** | | **~280 fragments** | |
| — | *What's included* (`ul`) | *150* | *service* | *7* | **excluded from both the word count and the similarity corpus** |

**The composition index is what bounds the worst case, and it is provable rather than hoped for.**
Each town carries a pair `(a, b)` with `a, b ∈ 0..7`, and **the map town → (a, b) is injective**
— 58 towns into a 64-cell grid. Two distinct towns therefore differ in at least one of `a` and
`b`, so **no pair of pages can share both block 3 and block 4.**

Injectivity alone bounds the *worst* pair. It does not bound the *mean*, and the two are not the
same problem: an injective-but-clustered assignment — say `(i mod 8, ⌊i/8⌋)` over the
distance-ordered list — puts the 18-town `move-out` cohort's 18 towns across only three `b` values,
which measures **E[J] = 0.078** against delta 23's 0.08 mean ceiling. Injective, provable, and one
rounding error from red.

**Use the Latin-square form**, over the distance-ordered index `i`:

```
a = i mod 8
b = (⌊i / 8⌋ + a) mod 8
```

Injective by construction (for a fixed `a`, `b` runs over all eight values as `⌊i/8⌋` does), and
**balanced inside any contiguous prefix**, which is exactly what a batch is. Measured over the
real 58: max 8 towns per `a` and per `b`; over the first 18, max 3 each; the `move-out` cohort's
mean falls to **E[J] = 0.048**, and the all-58 cohort to 0.044.

Both properties are asserted in `towns.js` at module load (§12 delta 29) — the formula is the
recommended default, the assertion is the gate, and the remedy for a failure is to permute the
ordering rather than to widen the ceiling.

Authoring cost: 58 town openers + 58 locality paragraphs + 58 hub-owned blocks + 56 + 56 service
variants + 45 county notes ≈ **81,000 words**. Hand-writing 258 new combos and 57 hubs at the
depth bar would be ~240,000. Neither number is small; the point of stating them is that the
mechanism is a 3× saving on real prose, not a 12× saving on mad-libs.

**Three prohibitions on the composition layer:**

1. **No sentence may be produced by substituting a town name into an otherwise fixed sentence.**
   The town appears in the `<h1>`, the lead, the locality paragraph and the interlink headings —
   places where a proper noun belongs — and the prose is *selected*, not *filled*.
2. **`localities` are rendered as place names only.** Never the district code they came from.
3. **Block 2 is where a town's real character goes** — the housing stock, the age of the estates,
   the parking. It is deliberately town-owned rather than a "town type" lookup, because a type
   taxonomy is the thing that makes ~58 pages read as ~6 pages.

### 10.3 The measured ceilings — CI, not aspiration

Same method as the audit (§12 of `seo-audit-2026-08-06.md`), run over built HTML: strip
`<script>`/`<style>`/`<nav>`, drop sentences appearing on >30% of pages, then 5-gram shingle
Jaccard over the remaining body text.

**Word count** — over the page's **authored prose only**: `<main>` text minus header, footer,
breadcrumb, *what's included*, ProcessSteps bodies, FAQ answers, review quotes and interlink
labels. Everything in that strip list is shared by ≥40 pages, so counting any of it would let the
depth bar be met without writing anything.

| Template | Counted prose | Bar | Margin |
|---|---|---|---|
| Combo | **995** | ≥ 800 (Lock 11 / SC-4) | +195 |
| Town hub | **645** | ≥ 600 | +45 |
| `/locations` | ~340 | ≥ 300 | +40 |

The hub's figure needs the same arithmetic as the combo's, because delta 22 enforces it on 57
generated pages and a +5 margin is not a margin:

| Block | Words | Axis | Shared with |
|---|---|---|---|
| Hero lead | 35 | town | nothing |
| The town, and us in it (`h2` + 2 `p`) | 260 | **town**, hub-owned | nothing |
| Which clean do you need (`h2` + 2 `p`) | 220 | **town**, hub-owned | nothing |
| Local coverage (`h2` + `p`), from `localities` | 130 | **town**, factual | that town's own 6 combos |
| **Counted prose** | **645** | | |

The hub is deliberately **not** a reuse of its combos' opening block. A hub whose text is a subset
of the six pages beneath it is the worst possible signal for the page meant to be the canonical
town entity. Sharing only the locality paragraph puts a hub against its own combo at
**J = 130 / (645 + 995 − 130) = 0.086**, and against another town's hub at **0.000**.

**Similarity**, with `W = 995` and Jaccard `J = S / (2W − S)` for two pages sharing `S` words of
contiguous prose. Every row below is derived from the table in §10.2, not estimated:

| Pair | Shared `S` | `J` |
|---|---|---|
| Different town, different service | 0 | **0.000** |
| Same service, same county only | 90 | 0.047 |
| Same service, same variant `b` | 260 | 0.150 |
| Same service, same variant `a` | 300 | 0.178 |
| Same service, same `b` + same county | 350 | 0.213 |
| **Same service, same `a` + same county — the worst pair the design permits** | **390** | **0.244** |
| Same town, different service (shares blocks 2 and 6) | 310 | 0.185 |
| Same `a` **and** same `b` | — | **impossible by construction** |
| Town hub vs a combo in the same town | 130 | 0.088 |

| Assertion | Threshold | Design produces | Basis |
|---|---|---|---|
| All-pairs median | ≤ 0.06 | **0.00** (most pairs differ in both town and service) | Live site 0.049 — never worse than the thing we are scaling |
| Within-service, across-towns median | ≤ 0.10 | **0.00** — 58% of such pairs share nothing | Arbor Trail's overall median is 0.100. Never worse than the competitor |
| Within-service, across-towns **mean** | ≤ 0.08 | **0.044** all-58 · **0.048** the 18-town `move-out` cohort | The mean is the honest summary when the median is zero. Both figures assume the balanced assignment in §10.2; a clustered one measures 0.078 on the small cohort |
| **Worst pair, any two generated pages** | **≤ 0.35** | **0.244** | Phase 2's service pages measured 0.327; hold what already ships, not the 0.6 ceiling |
| Town-masked delta on the medians | ≤ ±0.02 | — | **The anti-mad-libs gate.** If pages were variable substitution, masking the town would collapse them toward identity and this moves a lot |

The `≤ 0.35` ceiling now has **0.106 of headroom** against the design's own worst case, which is
the margin that lets a writer vary a fragment's length without the gate turning red for a reason
nobody can act on.

Cost: 348 combo pages is 60,378 pairs. Shingle sets over ~995 words each is a few seconds in node.
If it ever exceeds 60s in CI, the within-service cohorts (**9,198** pairs — 5 × C(58,2) + C(40,2) +
C(18,2), the split sets) run exhaustively and the
cross-service population samples at 10% — never the reverse, because the within-service cohort is
the one that can actually collide.


### 10.4 Reviews on generated pages

**Three cards on every combo page and every town hub**, in a `warm` band, matching the service
pages. Not six: a combo page already carries 995 words of counted prose plus a photo band.

**Which three varies by town.** `reviews.js` gains `reviewsForCombo(townSlug, serviceSlug)` — the
service's ordered candidate list, rotated by the town's index — so the trio leads with the review
that names the job while 348 pages do not all quote the same three customers. Deterministic, so
the build is reproducible.

`reviewsForService` already guards its key set against `services.js` at module load. The two
service-slug renames and the new `apartment-cleaning` page therefore all require a trio in
`reviews.js` in the same change, or the build goes red — which is the designed behaviour.

Two hard constraints inherited from plan 02-16 and not negotiable:

- **No review carries a town, and none may be invented one.** `ReviewRail`'s `town` prop, which
  narrows its own heading, **is not used**. The heading is `What our customers say` everywhere
  (§5). Phase 4 SC-3's "town-filtered reviews … where available" is satisfied by *where available*
  being nowhere until real town data exists.
- The 320-character data-layer cap holds, met by **selection, not truncation**.

### 10.5 Photography

Every combo and hub page renders `BeforeAfterSlider` with **no `pairs`**, emitting
`data-bhc-photo-state="pending"`. Delta 8 currently asserts the marker on exactly seven routes and
zero elsewhere; Phase 3 grows that to a per-template rule (§12 delta 21) covering 348 combo pages
and 7 service pages. This is SC-3's whole point: **no page is ever blocked on the Canva pull**,
and the marker stays the machine-readable hand-off to Phase 4.

The town hub does **not** carry a slider (`design-system.md` §3.4 does not list one, and a
photo band on 58 signpost pages is weight without content).

## 11. Batching, Publication and Partial States — SC-5

### 11.1 One flag, and everything derives from it

`towns.js` carries `batch: 1..5`; one constant, `PUBLISHED_BATCHES`, gates it; `PUBLISHED_TOWNS`
is the single filtered array. **Every derived list reads `PUBLISHED_TOWNS` and nothing reads the
raw array:**

- `generateStaticParams` for `/locations/[town]` and `/location/[region]/[town]/[service]`
- `nearestTowns()` — both the combo and hub interlinks
- the `/locations` grid and its county groups and jump links
- the home page's locations teaser
- the service pages' "towns we cover" block
- the sitemap

This is what makes "a town hub linking to a combo page that isn't built yet" **structurally
impossible** rather than something delta 6 catches after the fact. Delta 6 stays green by
construction, and it stays a real assertion because nothing is exempted from it.

**Atomicity: a town publishes with all six of its combo pages, or it does not publish.** There is
no half-published town, which is why `TownCard.serviceCount` is always `6` and why no template
needs a "some services coming to this town" state.

### 11.2 The batches

Batch order is ascending distance from the `leamington-spa` centroid — the map-pack-contestable
towns index first, the 46-mile organic-only ones last.

| Batch | Towns | New combos | New hubs | Other | **New pages** |
|---|---|---|---|---|---|
| **1** | **21** — the 18 legacy towns + `coventry` + `henley-in-arden` + `solihull` | 36 | 20 | `/locations` + `/services/apartment-cleaning` | **58** |
| 2 | 10 | 60 | 10 | — | 70 |
| 3 | 10 | 60 | 10 | — | 70 |
| 4 | 9 | 54 | 9 | — | 63 |
| 5 | 8 | 48 | 8 | — | 56 |
| | **58** | **258** | **57** | **2** | **317** |

Batch 1's 36 new combos are the 18 legacy towns' `post-construction` pages (their other five are
already live and preserved) plus the three new towns' six each. Its 20 new hubs are 21 towns minus
the live `/locations/leamington-spa`.

**Batch 1 is 21 towns rather than 19 deliberately.** Nineteen would produce 44 new pages, below
SC-5's 50–100 floor; the two nearest unpublished post towns (Henley-in-Arden ~11 mi, Solihull
~12.5 mi) bring it to 58 and are the two that most deserve to index first anyway.

Batches 2–5 land at 2–4 week intervals with indexation monitored between them
(REQ-content-depth-bar, `claude-seo`'s guidance). Each is a one-line change —
`PUBLISHED_BATCHES` incremented — plus a raised route floor (§12 delta 26).

> **The indexation clock starts at cutover, not at merge.** `web/app/layout.jsx` emits
> `<meta name="robots" content="noindex, nofollow">` on every page (D-15) and
> `web/public/robots.txt` is the host-level half. Nothing this phase builds is indexable until that
> is lifted, so "batch 1 then wait two weeks" is only meaningful from cutover onward. **Phase 3
> completes with batch 1 published**; batches 2–5 are post-cutover data changes.


### 11.3 Partial states must never look broken — the rules that make it so

| Risk | Rule |
|---|---|
| The index claims 58 towns while 20 are live | **No number in copy that is not interpolated from `PUBLISHED_TOWNS`.** The `<h1>` is `Areas We Cover` — no count. The intro names only counties with ≥1 published town |
| A county group renders empty | A county with zero published towns produces **no group and no jump link**. The groups are derived, not enumerated |
| "Nearest towns" points at an unbuilt town | `nearestTowns(town, PUBLISHED_TOWNS, n)` |
| A hub's ServiceCard 404s | Atomicity (§11.1) |
| Fewer than `n` nearby towns exist early in the rollout | `nearestTowns` returns what it has; `InterlinkBlock` renders the shorter list. It returns `null` only at zero, and zero is impossible from batch 1 (20 towns) |
| The header gains an "Areas We Cover" item before `/locations` exists | The nav item and the route land in the **same** change. Delta 6 would catch it, but this is cheaper than a red build |
| A published set of zero | **Build failure**, deliberately. `assert(PUBLISHED_TOWNS.length > 0)` in `towns.js` at module load. There is no empty-index rendered state and no "coming soon" copy anywhere (Phase 1's debt-marker record stands) |

Later batches change earlier pages' nearby lists. That is correct — the links are computed, and
recomputation is the property that makes them un-rottable. It also gives Phase 5's `<lastmod>` real
values to publish.
