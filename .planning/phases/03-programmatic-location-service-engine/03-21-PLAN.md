async redirects() {

  <action>
Add `async redirects()` to the config, exactly as the interface shows, with one thing the research
flagged and left open:

**The two-segment rule redirects garbage into a 404.** `/location/:region/:town` →
`/locations/:town` sends `/location/warwickshire/nowhere-town` to `/locations/nowhere-town`, which
404s because `dynamicParams` is false. A redirect-to-404 chain is a soft-404 generator, and at 58
towns and five batches it is a shape that grows. **Scope it**: build the rule's `:town` segment as a
regex alternation over `PUBLISHED_TOWNS`' slugs. An unknown town
then 404s directly, which is the honest answer, and the rule widens automatically with each batch
because it reads the same published set everything else does.

**Import it as `./content/towns.js`, a relative specifier — NOT `@/content/towns.js`.** The `@/*`
mapping in `web/jsconfig.json` is a **bundler** alias, and `next.config.mjs` is loaded by Node's ESM
loader before any bundling happens: the alias form throws `ERR_MODULE_NOT_FOUND` and `next build`
never starts. The config file sits outside the alias; every other consumer of `towns.js` in this
phase is bundled and uses `@/`.

Importing the module here also means its eleven module-load guards run at config load, which is a
free extra gate.

Document in the header, in the style the existing header uses for what is deliberately absent:
  - why `statusCode: 301` and not `permanent: true` — the latter emits 308, and the requirement, the
    config and the lock should agree without interpretation;
  - that `statusCode` and `permanent` are mutually exclusive;
  - that these compile into declarative edge routing rules with no middleware and no function, which
    is the whole reason a proxy is not used here;
  - that the two-segment rule is scoped, and what would happen if it were not.

Do not add `trailingSlash`, do not add a proxy, and do not add a `vercel.json` — a second redirect
surface would be invisible to `next build` and unassertable from `.next/`.
