<objective>
Prove the CI gate actually blocks, and make it binding.

Purpose: D-13 says a lock suite that runs but does not gate is not a lock. Plan 03 delivered a
workflow that exits non-zero on failure — that is necessary but not sufficient. Two things remain:
demonstrating end-to-end that a failing lock turns the GitHub Actions run red, and marking the jobs
as required status checks on `main` so a red run blocks a merge. The second is a repo-admin action
in GitHub's settings that no agent can perform.

Output: a recorded red-then-green CI run pair, and branch protection configured on `main`.

This plan runs last because it deliberately pushes a broken commit. Everything else in the phase
must already be green so that the red run is unambiguously caused by the probe and by nothing else.
</objective>

.github/workflows/ci.yml — two jobs on `on: push` with `branches: ['**']`:
  locks   checkout -> setup-node 22 -> `node --test design-system/test/*.test.js`   (no npm ci)
  build   checkout -> setup-node 22 (cache npm) -> npm ci -> npm run build --workspace @bhc/web
          -> node --test web/scripts/check-html-locks.mjs -> node web/scripts/check-budget.mjs

Because the locks job globs `design-system/test/*.test.js`, ANY new `*.test.js` file dropped in that
directory is picked up automatically — which is what makes a throwaway probe file the cleanest way
to demonstrate gating without editing `locks.test.js` and risking a bad revert.

Verified locally during research: injecting a failing test made the suite exit 1. This plan proves
the same holds in the CI runner, where it actually matters.

Useful gh invocations:

  gh run watch <id> --exit-status        # exits non-zero if the run failed

  <action>
    First confirm the baseline: the newest CI run for the current branch must have concluded
    `success` for both the `locks` and `build` jobs. If it has not, stop — a red run caused by
    something other than the probe proves nothing, and this plan must not be used to paper over an
    unrelated failure.

    Create `design-system/test/__ci-gate-probe.test.js` — a throwaway file, deliberately named with a
    leading double underscore so it sorts distinctly and is obviously not a real lock. Use a
    throwaway file rather than editing `locks.test.js`: a botched revert of the real lock suite is
    the one failure mode worth engineering out of this exercise entirely.

    Its contents: `node:test` and `node:assert/strict` imports only, matching the house style, plus a
    single test whose assertion always fails, with a header comment stating in plain terms that the
    file exists solely to prove D-13 gating and must be deleted in the same plan that created it.

    Confirm locally that `node --test design-system/test/*.test.js` now exits non-zero.

    All repository mutations belong in this action, not in `<verify>`. The `<verify>` block below is
    strictly read-only, so re-running verification after a revision cannot fail spuriously on
    "nothing to commit" or on staging an already-deleted file.

    Perform the red/green cycle here:

      1. Stage the probe by explicit path and commit it alone — no other changes in that commit —
         with a message that makes its purpose and its temporary nature unmistakable. Push.
      2. Write `git rev-parse HEAD` to the file `/tmp/bhc-red-sha`. Poll
         `gh run list --commit "$(cat /tmp/bhc-red-sha)"` until a run registers for that exact SHA —
         never `gh run list --limit 1`, which can return the previous, already-green run and
         manufacture a false pass in the unsafe direction. Poll for up to five minutes before
         giving up.
      3. Wait for that SHA-matched run to complete. Record its run ID, run URL, the `locks` job
         conclusion, and the overall run conclusion. The `locks` job MUST conclude `failure`.
      4. Delete the probe file, commit the deletion alone by explicit path, and push.
      5. Write `git rev-parse HEAD` to the file `/tmp/bhc-green-sha` and repeat the SHA-matched
         polling. Both jobs must conclude `success` on that SHA. Record its run ID and URL.

    **Persist both SHAs to those two files, not to shell variables.** Shell state does not survive
    between separate command invocations, so a `RED_SHA` exported here would be an empty string by
    the time the `<verify>` block runs — `select(.headSha=="")` would match nothing, `grep -q` would
    fail, and the task would report failure despite having succeeded, halting execution on the very
    plan that proves D-13. Each verify command below reads the SHA back from its file. (01-03 Task 3
    avoids the same trap by recomputing the SHA inline in every command; it cannot do that here
    because two *different* historical commits must be referenced after the tree has moved on.)

    Afterwards the working tree must be clean and `design-system/test/` must contain exactly one
    file, `locks.test.js`. The probe leaves no trace beyond the two commits in history, which are
    themselves the evidence.
  </action>

    - The two SHAs are persisted to `/tmp/bhc-red-sha` and `/tmp/bhc-green-sha` during the action,

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| contributor → `main` | Branch protection is the only thing preventing unverified code from reaching the default branch. Until it is configured, this boundary is unenforced. |
| deliberately broken commit → repository history | This plan intentionally pushes a failing commit. It must not be able to reach `main` unreverted, and must not be mistaken later for a real regression. |
| GitHub Actions runner → repository | The workflow runs on every push, including on the probe commit, with a read-only token. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

Verification accepts either classic branch protection or a ruleset, because classic protection is unavailable on private repos on GitHub Free and a classic-only check would report failure on a correctly-configured repo. This is the item D-13 explicitly forbids omitting, and it closes threat T-01-14 opened in Plan 03. |
