<objective>
Turn every Phase 1 success criterion into an automated, zero-dependency assertion, and put those
assertions behind a CI job that fails the build.

Purpose: Success Criterion 3 is not "the lock tests exist" — it is "the lock tests run as part of
this project's build/CI pipeline". D-13 goes further: a suite that runs but does not gate is not a
lock. This plan builds the harness that later phases extend from 3 locks to all 11.

Output: two zero-dependency enforcement scripts, a two-job GitHub Actions workflow, and root npm
scripts that run the whole suite in one command.

Two decisions this plan locks, because 01-PATTERNS.md asks the planner to state them:
1. `check-html-locks.mjs` uses `node:test` + `node:assert/strict` and is invoked as
   `node --test web/scripts/check-html-locks.mjs`. That is the house convention, it produces
   per-lock TAP output naming exactly which lock failed, and it exits non-zero on failure.
2. `check-budget.mjs` is a plain script (no `node:test`) that prints its measurements and calls
   `process.exit(1)` on breach — its value is the printed numbers as much as the gate.

Why GitHub Actions and not the Vercel build: Vercel's Root Directory sandbox cannot use `..` to
reach the sibling design-system package, and npm hoists workspace deps to the workspace root rather
than `web/node_modules`, so there is no `..`-free path to the test files either. More decisively, a
red Vercel preview does not block a merge — which is exactly what D-13 forbids. Leave the Vercel
Build Command at its default `next build`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo → GitHub Actions runner | Workflow definitions execute with a repository token. This is the only place in Phase 1 where automation runs with any credential at all. |
| npm registry → CI runner | `npm ci` resolves the dependency tree on a machine nobody watches. |
| built HTML → assertion layer | The enforcement scripts are the only thing standing between a silent regression and production. Their integrity is itself a security property. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-12 | Elevation of Privilege | `.github/workflows/ci.yml` token scope | mitigate | Declare `permissions: contents: read` at workflow level. The workflow needs no write scope, publishes nothing, and references no `secrets.*`. Asserted by Task 3's acceptance criteria. |
| T-01-SC | Tampering (supply chain) | `npm ci` in the `build` job | mitigate | `npm ci` installs strictly from the committed root `package-lock.json`, so the CI dependency set cannot drift from the audited one.
