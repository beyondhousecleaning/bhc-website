# Phase 2 — UI Design Contract

> Visual and interaction contract for Phase 2: Component Library Completion & Core Templates.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> **Revision 1 (2026-08-09)** — 12 checker recommendations folded in; 0 blocking findings.

## How to read this

This phase designs **nothing new at the token level**. `docs/design/design-system.md` and
`design-system/tokens.css` are locked (D-04, D6, D11, D12) and every value below is quoted from
them, not re-derived. What this document adds is the layer the locked spec deliberately left
open: **which token goes where, in which of the sixteen new components, on which of the
eighteen new pages, with what words in it.**

Everything is prescriptive. Where the locked artifacts were silent, a default was chosen and
recorded in §13 with a one-line rationale. Items that genuinely need Sam are in §14 — there are
three and none of them blocks a plan.

Every contrast ratio quoted here is either reproduced from `design-system.md` §1's measured
table or was measured for this document; none is eyeballed.

| Property | Value |
|----------|-------|

| Component library | **none.** No Radix, no Base UI, no headless library, no Tailwind, no CSS-in-JS |

### Inline SVG accessibility rule

**`alt` is not a valid attribute on `<svg>`.** It is silently dropped, so an SVG carrying it is
an unlabelled graphic and Lock 7 will not catch it — Lock 7 greps `<img>` tags only.

| The SVG is… | Markup |
|---|---|
| Decorative — sits beside text that already says it (TrustBar glyph, FAQ chevron, star in a labelled badge) | `aria-hidden="true" focusable="false"` |
| Meaningful — it is the only content of its figure, link or button | `role="img"` + `aria-label="…"`, and **never** `alt` |

`RatingBadge` is the shipped precedent for both halves at once: individual `Star` glyphs are
`aria-hidden`, and their wrapper carries `role="img"` with the full `aria-label`.

### shadcn gate — resolved from upstream, not asked

`components.json` is absent and the stack is Next.js 16, so the gate fires. It is answered
**No**, and the answer comes from locked upstream decisions rather than from a question to Sam:

| Blocker | Source |
|---|---|
| The package must have zero dependencies and no build step and run from a clean checkout | 01-CONTEXT.md `<specifics>`; `design-system/package.json` has no `dependencies` or `devDependencies` |
| shadcn components are Radix-backed client components | `check-html-locks.mjs` SC-4g asserts **every** client module resolves inside `/node_modules/next/`. A single shadcn primitive turns that required status check red |
| Tokens are locked and single-sourced | D-04. A shadcn preset would introduce a second, conflicting token layer, and the `--bhc-ink`-declared-exactly-once lock would fail |

`Tool: none`. Registry safety gate: not applicable (§6).

### Weight policy

Two structural weights: **400** for everything that is read, **700** for everything that is a
heading. The token set ships four; the other two are permitted only in the closed list below,
which matches the shipped CSS exactly and adds nothing new:

| Weight | Token | Permitted only in |
|---|---|---|
| 400 | `--bhc-weight-normal` | All body, lead, meta and caption text |
| 500 | `--bhc-weight-medium` | The current (unlinked) breadcrumb crumb — shipped, unchanged |
| 600 | `--bhc-weight-semibold` | Button labels · Hero eyebrow · InterlinkBlock/ServiceCard/TownCard link labels · footer column headings · TrustBar labels · FAQ `<summary>` question |
| 700 | `--bhc-weight-bold` | `h1`–`h4`, RatingBadge value, footer business name and phone |

> Deviation from the generic "declare exactly 2 weights / 3–4 sizes" heuristic is deliberate,
> recorded in §13-A/B, and **explicitly accepted by the checker**: `tokens.css` is the locked
> single source of truth, trimming it here would fork it (D-04) and re-create the design→build
> drift D9 exists to prevent, and the binding table above is stronger enforcement than a bare
> count cap.

**Never:** a `<div>` or `<span>` styled at heading size. That pattern is the exact live-site bug
that cost 101 of 115 pages their `<h1>` (`Hero.prompt.md`). If it looks like a heading it is a
heading element.

`--bhc-action-hover` `#C2410C` is **text and edges**:

`--bhc-sponge` `#F78C34` is warmth **on `--bhc-ink` only**:

1. Footer column headings (shipped — ink ground, 6.59:1)

3. `TrustBar` icon glyphs when the bar sits on `--bhc-ink`

### Two tokens Phase 2 does not use at all

`--bhc-blue` `#197EC7` and `--bhc-cyan` `#0DA6E8` are **not used by any of the sixteen new
components.** Both exist in the locked token set but neither has a safe body-text role — white on
blue is 4.33:1 (large text only) and white on cyan is 2.75:1 (fails everything). Sixteen new
components authored in one phase is exactly when a "just this once" cyan panel with white text
ships, and that is precisely the failure the logo audit already caught in the current wordmark.
Introducing either is a Phase 5+ decision with a fresh contrast measurement, not a Phase 2 one.

One `primary` per visual section (`Button.prompt.md`). Verbs, never nouns: *Get a Free Quote*,
not *Quote*. **Never** "Submit", "Click here", "Learn more".

> Revision 1 removed `Read Our Reviews → #reviews` from this set. `ReviewRail` returns `null` on
> empty data (§7.14) and the review data arrives in Phase 4, so in Phase 2 that anchor
> dead-ends on every page — and §12 lock 6 only checks `href^="/"`, so nothing would catch it.
> Seeding fabricated testimonials to make the anchor resolve is not an option on a site whose
> entire positioning is "a genuinely local team". The CTA returns in Phase 4 with the data.

**`Call` needs an accessible name.** A one-word link is ambiguous out of context for screen-reader
users listing links. Note the interaction with §12 delta 2(d): that lock must read the element's
**text content**, not the raw tag string, or `aria-label="Call Beyond House Cleaning"` will not
trip it but a future `aria-label` containing digits would.

**Displayed phone digits.** Any label containing digits must render exactly
`+44 7861 936533` — the output of `formatPhone(CANONICAL_PHONE)`. That format, and only that
format, survives the `SC-2b` digit-equality lock, which normalises a leading `44` but not a
leading `0`. A label of `Call 07861 936533` fails the lock. If a shorter label is needed, use one
with **no digits at all** (`Call`) plus an `aria-label`, and the href still dials the one
canonical number.

#### The responsive mechanism, stated explicitly

Both obvious CSS-only routes break a declared invariant, so neither is used:

| Rejected route | Why |
|---|---|
| Put the `<ul>` **inside** `<details>` and hide `<summary>` at desktop | A closed `<details>`'s non-summary children are hidden by the UA through the details-content slot, not by a `display` rule a stylesheet can simply override. Hiding the toggle leaves the nav permanently hidden on desktop. `::details-content { content-visibility: visible }` would work but is too new to depend on |
| Render a second desktop `<ul>` | Breaks "one `<nav aria-label="Primary">` per page" (§9.1) and duplicates every nav link in the DOM, which §12 lock 6 then counts twice |

**The mechanism: `<details>` is a state carrier with no content, and the one `<ul>` is its
sibling.** The UA only hides a `<details>`'s own children, so a sibling is untouched and a plain
sibling combinator drives it:

```html
<nav aria-label="Primary" class="bhc-nav">
  <details class="bhc-nav__disclosure">
    <summary class="bhc-nav__toggle" aria-controls="primary-nav" aria-label="Menu">…</summary>
  </details>
  <ul class="bhc-nav__list" id="primary-nav"> <!-- rendered ONCE --> </ul>
</nav>
```

```css
.bhc-nav__list { display: none; }
.bhc-nav__disclosure[open] ~ .bhc-nav__list { display: block; }

@media (min-width: 1024px) {
  .bhc-nav__disclosure { display: none; }   /* toggle gone entirely */
  .bhc-nav__list       { display: flex; }   /* unconditionally visible */
}
```

One `<nav>`, one `<ul>`, every link in the DOM exactly once, zero JavaScript, and no dependency
on `::details-content`. `<summary>` supplies `aria-expanded` natively; `aria-controls` names the
list it governs (support is patchy but it is inert where unsupported).

The **Services submenu is a nested `<details>` that does contain its own `<ul>`** — ordinary
usage, no hidden-content problem — absolutely positioned below its summary at ≥1024px. It needs
no `/services` index page (which 404s today) and puts six keyword-bearing links in the global nav.

### 7.9 FAQAccordion — Success Criterion 4

```ts
interface FaqItem { question: string; answer: ReactNode; }
interface FAQAccordionProps { heading?: string; items: FaqItem[]; defaultOpen?: number; }
```

```html
<section class="bhc-faq" aria-labelledby="faq-heading">
  <h2 id="faq-heading">Questions we get asked</h2>
  <details class="bhc-faq__item" open>
    <summary class="bhc-faq__summary"><h3 class="bhc-faq__q">How long does a deep clean take?</h3></summary>
    <div class="bhc-faq__a"><p>…</p></div>
  </details>
</section>
```

- **Zero JavaScript.** `<details>`/`<summary>` is native, works with JS disabled, and stays a
  server component — so SC-4g's "no first-party client module" lock is untouched.
- **No `name` attribute.** Exclusive-accordion behaviour would collapse the previous answer;
  multiple-open is better for scanning. `defaultOpen` (default `0`) sets `open` on the first item
  so an answer is visible above the fold.
- **`<h3>` inside `<summary>` is valid.** Verified against the HTML Standard: `summary`'s content
  model is *"phrasing content, optionally intermixed with heading content."* It gives every
  question a heading in the document outline.
  **Caveat, so nobody later relies on it:** `summary` maps to a button-like role, and ARIA treats
  the descendants of a button as presentational, so *heading exposure inside `<summary>` is
  inconsistent across browser/AT pairs*. Do not design an interaction that depends on
  screen-reader heading navigation through the FAQ, and do not treat the `<h3>` as the
  accessible name — the `<summary>`'s text content is.
- **The crawler/LLM half of SC-4 holds unconditionally** and does not depend on the point above:
  a closed `<details>` still ships its full answer text in the server-rendered HTML. Nothing is
  hidden from a crawler or a model.
- **No `FAQPage` JSON-LD. Ever.** D13 / Google retired FAQ rich results 2026-05-07. Asserted by
  a CI lock that greps every built page for `FAQPage` and expects zero (§12 lock 7).
- Marker: `summary { list-style: none }` + `summary::-webkit-details-marker { display: none }`,
  own chevron rotating on `[open]` through `--bhc-dur` so `prefers-reduced-motion` applies.
- `<summary>` row ≥44px, and it is already covered by the shipped `:focus-visible` rule.

## 8. Interaction & Client-Boundary Contract

**Phase 2 adds zero client components.** `check-html-locks.mjs` SC-4g asserts every module in the
client-reference manifest resolves inside `/node_modules/next/`, and it stays green with no edit.

| Component | Interactive? | Mechanism | Client boundary |
|---|---|---|---|
| Header — mobile nav | disclosure | `<details>` state carrier + sibling `<ul>` (§7.1) | **No** |
| Header — services submenu | disclosure | nested `<details>` with its own `<ul>` | **No** |
| FAQAccordion | expand / collapse | `<details>` / `<summary>` | **No** |
| ReviewRail | horizontal browse | CSS `overflow-x` + `scroll-snap`, focusable region | **No** |
| BeforeAfterSlider | compare | side-by-side ≥768px, `scroll-snap` below | **No** |
| StickyCallBar | none — two links | `position: fixed` + media query | **No** |
| Everything else | none | — | **No** |

### `<details>` rules

1. Never `name=` (exclusive accordion) — it collapses a sibling the reader may still be using.
2. Suppress both default markers (`list-style: none` and `::-webkit-details-marker`); supply an
   SVG chevron rotated by `[open]`.
3. All motion through `--bhc-dur` / `--bhc-ease`, so the token-level
   `prefers-reduced-motion` override (which zeroes all three duration tokens) actually applies.
4. Never rely on `::details-content` — too new to depend on (§7.1).
5. Accepted limitation, documented rather than worked around: **Escape does not close a
   `<details>`** and it does not close on outside click. Both would need JS. For a menu and an
   FAQ on a multi-page-navigation site this is a fair trade for keeping the whole render
   server-side.
6. `<summary>` is already in the shipped `:where(a, button, input, select, textarea, summary):focus-visible`
   rule — do not add a bespoke focus style.

### Navigation is plain `<a href>` — no `next/link`

Package components cannot import `next/link` (zero dependencies, framework-agnostic — D-02,
D-05), and wrapping them app-side would split link behaviour across two mechanisms and add a
client module for a marketing site whose pages are static and CDN-served. Accepted cost: no
prefetch. Accepted benefit: the JS budget stays flat as the page count goes 1 → 18 → ~410, and
the mobile nav's `<details>` state resets on navigation for free.

**Escape hatch (§13-J):** every link-bearing component takes `as?: ElementType` defaulting to
`'a'`. One line each. It turns the least reversible default in this contract — a property of
sixteen components' internals rather than a data value — into a one-line change if prefetching
is ever wanted.

`InterlinkBlock` *towns we cover for this service* (Phase 3 populates; renders `null` until then)

> **Revision 1 — the trail lost its middle crumb, and `Breadcrumbs` gains a rule.** The previous
> trail was `Home › Services › {Service}`, and neither option worked: `/services` 404s and Phase 2
> ships no index, so a linked crumb fails §12 lock 6, while an href-less crumb made *two* elements
> carry `aria-current="page"` on all six service pages.
>
> Fold into the WR-12 `Breadcrumbs` remediation §12 already earmarks: **a non-last crumb with no
> `href` renders as a plain `<span>` and never receives `aria-current`. Only the last crumb gets
> `aria-current="page"`, whether or not it is a link.** Phase 3 inherits this at ~336-page scale,
> where every combo trail has an intermediate crumb, and it reinstates the `Services` crumb once
> an index exists. The `BreadcrumbList` JSON-LD keeps all listed items either way.

Content depth: `Prose` must carry ≥800 unique words. Live service pages already median 1,183 —
do not regress them.

### 9.4 Utility (×10 + not-found)

`Breadcrumbs` → `Hero align="centered"` (no image, **rating included**) → `Prose` →
`QuoteFormEntry` *or* `CTABand`.

- The rating badge is on utility pages too: Lock 3 says *every* template, and Phase 4 SC-1 names
  utility explicitly.
- `/get-a-quote`: `Prose` explaining what happens next + `QuoteFormEntry` + `ProcessSteps`.
- `/customer-login`: a single clear outbound action to the existing booking portal, plus a
  `Call` fallback. No login form here.
- Legal pages (`/privacy-policy`, `/terms-of-service`, `/customer-service-agreement`):
  `Hero align="centered"` + `Prose width="narrow"`, no CTABand, no BeforeAfterSlider.
- `app/not-found.jsx`: `Hero` with `<h1>` *We Couldn't Find That Page*, the §5 error copy, and
  three links (`/services/deep-cleaning`, `/`, `/get-a-quote`). It is a real template and it
  gets a real `<h1>` — WR-07 found that nothing has ever inspected `_not-found.html`, and it
  renders `RootLayout`, so from Phase 2 it also carries a header, a footer and `tel:` links.

### 9.5 Do **not** add `app/global-error.jsx`

Next.js requires a custom `global-error` to be a **client component** — React error boundaries
need class lifecycle methods (`getDerivedStateFromError`, `componentDidCatch`) that only run in
the browser. Adding one turns SC-4g red and breaches D-07. Keep the framework default.
`_global-error.html` renders `RootLayout` and therefore has a `<footer>` and a `tel:` but no page
content and no `<h1>` — so it is the single documented exclusion from the one-`<h1>` lock and
from nothing else (§12 lock 4).

### 9.6 Templates explicitly NOT in this phase

Locations index, town hub and combo (Phase 3); article/blog layout (Phase 6). `ServiceCard`,
`TownCard`, `ReviewRail` and `InterlinkBlock` are all built here to their eventual Phase 3 API so
that phase writes data, not components.

## 10. Accessibility Contract

Everything below is measured or specified upstream; none of it is preference.

| Area | Requirement |
|---|---|
| Contrast | Every pairing in §4. Ink on orange, never white on orange. Never white on cyan. Never sponge on navy. `RatingBadge` on light surfaces only |
| Landmarks | One `<header>`, one `<nav aria-label="Primary">`, one `<main id="main">`, one `<footer>` per page. `Breadcrumbs` → `<nav aria-label="Breadcrumb">`. Footer columns → `<nav aria-label={heading}>` (shipped) |
| Skip link | First element in `<body>`; target `<main id="main" tabIndex={-1}>` |
| Headings | Exactly one `<h1>` (from `Hero`). No skipped levels. `Prose` starts at `<h2>`. Cards take `headingLevel` |
| Focus | The shipped `:focus-visible` rule, **plus the two scoped overrides below — nothing else** |
| Current page | At most one `aria-current="page"` per page (§9.3) |
| Touch targets | ≥44 × 44px for StickyCallBar actions, `<summary>` rows, footer links |
| Images | Non-empty `alt` on **every** `<img>` — Lock 7. Inline SVG uses the §1 rule; `alt` on `<svg>` is invalid and unenforced |
| Motion | All transitions via `--bhc-dur*` / `--bhc-ease`; the token-level reduced-motion override then applies automatically |
| Link text | No "click here" / "read more". Link text names its destination, or an `aria-label` does (`Call`) |

| Language | `<html lang="en-GB">` (shipped). UK spelling throughout |

### Focus-indicator contrast — a scoped override is required

`--bhc-focus-ring` is `3px solid var(--bhc-action-hover)` (`#C2410C`) at `2px` offset, so the ring
lands on **the surface behind the element**, not on the element's own fill. On the light bands
Phase 1 shipped, that surface is paper or warm, where the ring measures 5.18:1 and 4.89:1
respectively — fine.

Phase 2 introduces the first dark band. Measured for this revision:

| Ring on | Ratio | WCAG 1.4.11 (3:1) |
|---|---|---|
| `--bhc-action-hover` on `--bhc-paper` | 5.18:1 | ✅ the shipped default |
| `--bhc-action-hover` on `--bhc-paper-warm` | 4.89:1 | ✅ the shipped default |
| `--bhc-action-hover` on `--bhc-navy` | **1.15:1** | ❌ effectively invisible |
| `--bhc-paper` on `--bhc-navy` | 5.97:1 | ✅ |
| `--bhc-paper` on `--bhc-ink` | 15.81:1 | ✅ |
| `--bhc-ink` on `--bhc-paper` / `--bhc-paper-warm` | 15.81 / 14.94:1 | ✅ |
| `--bhc-ink` on `--bhc-action` (abutting fill) | 5.17:1 | ✅ |
| `--bhc-paper` on `--bhc-action` | 3.05:1 | ✅ for a non-text indicator |

Every page now carries a `CTABand`, so this is not an edge case. Two scoped overrides, and only
these two:

```css
/* 1. Dark bands — the ring lands on navy or ink, where the orange disappears. */
.bhc-section--navy .bhc-btn--primary:focus-visible,   /* wins over rule 2 by specificity */
.bhc-section--navy :focus-visible,
.bhc-footer :focus-visible {
  outline-color: var(--bhc-paper);      /* 5.97:1 on navy · 15.81:1 on ink · 3.05:1 on an orange fill */
}

/* 2. Primary buttons on light bands — an orange ring abutting an orange fill
      reads as one blob, especially on hover when the fill IS --bhc-action-hover. */
.bhc-btn--primary:focus-visible {
  outline-color: var(--bhc-ink);        /* 15.81:1 on the band · 5.17:1 against the fill */
}
```

`--bhc-ink` rather than `--bhc-paper` for rule 2: a white ring on a white band is 1:1. Rule 1's
first selector exists because ink-on-navy is 2.65:1 — a primary button inside the CTABand must
take the white ring, not the ink one.

Nothing else may change the focus indicator. `outline: none` is never acceptable.

### `formatPhone` still degrades silently — build the guard in this phase

§10 previously asserted *"`formatPhone` now throws rather than degrading."* **It does not.**
Verified against `formatPhone.js:63-68`: there is no `throw` on any branch. `formatPhone('')`
returns `"+44"` and `formatPhone(undefined)` returns `"+44"`, so an empty or malformed `phone`
renders `<a href="tel:+44">` wrapping empty link text — an empty interactive element, WCAG 2.4.4.

CR-04 closed the *divergence* hole (display is now derived from the dial string on every branch,
lock-tested at `locks.test.js:47`). It did not close the *degradation* hole.

**This is Phase 2 work, not a description of the status quo**, and the blast radius grew: three
components consume `formatPhone`/`toDial` from `phone.js` now, not one. Required:

1. `toDial` throws on a value whose national part is not a valid length, rather than returning
   `+44` or `+{digits}`.
2. `formatPhone` inherits the throw (it already calls `toDial` first).
3. New lock tests asserting the throw for `''`, `undefined`, `'+44'`, `'call us'`, and the
   one-digit-over / one-digit-under cases already enumerated at `locks.test.js:53-64`.
4. `MIN_TESTS` in `run-locks.mjs` raised accordingly (§12 lock 10).

Failing loudly at build time on ~410 statically prerendered pages is strictly better than
shipping a dead `tel:` link: the build breaks in CI, not the phone line in production.
