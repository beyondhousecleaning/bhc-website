Each component is a directory `design-system/src/components/<Name>/` holding EXACTLY the four
canonical files `<Name>.jsx`, `<Name>.html`, `<Name>.d.ts`, `<Name>.prompt.md`, plus a CSS block in
`design-system/styles.css`, a named export in `design-system/src/index.js`,
`<!-- @dsCard group="…" -->` on LINE 1 of the `.html` followed by
`<link rel="stylesheet" href="../../../styles.css" />`, `category: <same group>` frontmatter on the
`.prompt.md`, and an entry in BOTH `componentSrcMap` and `docsMap` in `.design-sync/config.json`.

**Append every new CSS block ABOVE the focus-override banner that plan 02-04 placed at the end of
`styles.css`.** That section must remain last in the file.

Hard rules: no `import React`; sibling relative paths with the extension always written; no client
directive, `useState`, `useEffect` or event-handler props anywhere; never `&&` in JSX (use a ternary
to `null`); the `['bhc-<block>', modifier, className].filter(Boolean).join(' ')` merge idiom;
variant maps with a fallback; `export default <Name>;` at the end of every file;
`JSX.Element | null` in the `.d.ts` when the component can return null; pure string manipulation in
a plain `.js` sibling, never in the `.jsx` (the `claude-seo` hook rejects a `.jsx` write containing
the case-insensitive substring `REPLACE`, which every `.replace(` contains); values exclusively
`var(--bhc-*)` with no literal hex; comments state measured evidence, not intent.

Groups are `Navigation` / `Content` / `Trust` / `Actions` only.
**Never write the client directive literally anywhere under `design-system/src` or `web/content` —
including prose, header comments and `## Don't` lists.** Plan 02-02 extends the client-boundary
source scan to those two roots, and it is a plain substring grep, so an explanatory sentence naming
the directive turns `check:html` red for the whole phase. `web/app/page.jsx:11-15` already follows
this convention for exactly this reason: refer to it as "the client directive" and never spell it.
Zero occurrences exist today; this collision has already bitten this repo three times.

**Class-name counting rule, for any acceptance criterion that counts a `bhc-` class in BUILT HTML:**
use the `class="[^"]*bhc-…` form. A bare grep double-counts, because the RSC flight payload is
inlined in the HTML and serialises the same value as `\"className\":\"bhc-…\"` — measured at 2 vs 1
during planning. Zero-assertions are safe in either form. Greps over SOURCE files are unaffected.

**FAQAccordion** — group `Content`, root `<section class="bhc-faq">`. This is ROADMAP SC-4.

Props per §7.9: `heading`, `items` (array of `{ question, answer }`), `defaultOpen` (default `0`).
`return null` when `items` is empty, following the `InterlinkBlock` convention. Markup:
`<section class="bhc-faq" aria-labelledby={id}>` with an `<h2 id={id}>`, then one
`<details class="bhc-faq__item">` per item containing
`<summary class="bhc-faq__summary"><h3 class="bhc-faq__q">{question}</h3></summary>` and
`<div class="bhc-faq__a">{answer}</div>`. The `id` is derived from a prop, not hardcoded.

Non-negotiables, each recorded as a comment with its reason:
- **Zero JavaScript.** `<details>`/`<summary>` is native, works with JS disabled, and keeps this a
  server component — so plan 02-02's SC-4g client-boundary lock stays green.
- **No `name` attribute.** Exclusive-accordion behaviour collapses the answer the reader may still
  be using; multiple-open is better for scanning. `defaultOpen` sets `open` on that index only, so
  one answer is visible above the fold.
- Marker suppression: `summary { list-style: none }` plus
  `summary::-webkit-details-marker { display: none }`, with an inline SVG chevron carrying
  `aria-hidden="true" focusable="false"` that rotates on `[open]` through `--bhc-dur`/`--bhc-ease`
  so the token-level `prefers-reduced-motion` override applies automatically.
- `<summary>` row is at least 44px tall. Do NOT add a bespoke `:focus-visible` style — `summary` is
  already in the shipped base rule.

**The structured-data prohibition goes in `FAQAccordion.prompt.md`, NOT in the `.jsx`.** The `.jsx`
must not contain the literal schema-type token, because plan 02-02's delta 7 and this task's own
acceptance criterion both grep for it and a well-meant explanatory comment would fail them. In the
`.jsx` header comment write only: *"This component emits no structured data of any kind. The reason,
the retirement date and the decision reference live in the prompt doc."* Then in
`FAQAccordion.prompt.md`, state it fully and by name: `FAQPage` JSON-LD must never be emitted — D13,
Google retired FAQ rich results on 2026-05-07 — and plan 02-02's delta 7 greps every built page for
that token expecting zero. Put it in the `.prompt.md`'s `## Don't` list too.

Record the accessibility caveat in `FAQAccordion.prompt.md` so it is not rediscovered: `<h3>` inside
`<summary>` is valid per the HTML content model, but `summary` maps to a button-like role and ARIA
treats a button's descendants as presentational, so heading exposure is inconsistent across
browser/AT pairs. Nothing may be designed to depend on screen-reader heading navigation through the
FAQ, and the accessible name is the `<summary>`'s TEXT CONTENT, not the `<h3>`. Add that the
crawler/LLM half of SC-4 holds unconditionally regardless: a closed `<details>` still ships its full
answer text in the server-rendered HTML.
